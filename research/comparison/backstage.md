# Backstage (CNCF) vs. Living AI Knowledge — feature-by-feature comparison

**Comparison date:** 2026-09-24
**Backstage version in scope:** v1.55.x (v1.55.0 feature release, Sept 2026); `master` at time of writing.
**Primary sources consulted directly:** `packages/catalog-model/src/kinds/relations.ts`, `plugins/catalog-backend/src/schema/openapi.yaml`, `plugins/catalog-backend/src/actions/` (directory listing + `createRegisterCatalogEntitiesAction.ts`, `createRefreshCatalogEntityAction.ts`), `packages/catalog-model/src/model/types.ts`, `plugins/catalog-backend-module-ai-model/README.md`, `plugins/catalog-backend-module-aws/README.md`, `docs/ai/mcp-actions.md`, backstage.io docs on well-known annotations, life-of-an-entity, external integrations, Kubernetes; `awslabs/backstage-plugins-for-aws`.

## 0. Corrections and additions to the incoming dossier

The dossier is broadly accurate on the load-bearing claims. Four corrections, two of which matter.

| Dossier claim | Verdict |
| --- | --- |
| Exactly 7 relation pairs / 14 exported constants | **Confirmed verbatim.** `relations.ts` exports `RELATION_OWNED_BY`/`OWNER_OF`, `CONSUMES_API`/`API_CONSUMED_BY`, `PROVIDES_API`/`API_PROVIDED_BY`, `DEPENDS_ON`/`DEPENDENCY_OF`, `PARENT_OF`/`CHILD_OF`, `MEMBER_OF`/`HAS_MEMBER`, `PART_OF`/`HAS_PART`. Nothing else. |
| No create-entity or update-entity REST endpoint | **Confirmed.** The OpenAPI spec's complete path list contains no POST/PUT/PATCH on `/entities`. The only mutating operations are `RefreshEntity`, `DeleteEntityByUid`, `CreateLocation`, `UpdateLocation`, `DeleteLocation`, plus the non-persisting `AnalyzeLocation` and `ValidateEntity`. I counted 20 path+method operations, not 21 — not load-bearing. |
| Three MCP write tools | **Wrong — there are four catalog-side write paths, and the extra one is interesting.** The actions directory contains `createRefreshCatalogEntityAction.ts`, action id `'refresh-catalog-entity'`, attributes `{destructive: false, readOnly: false, idempotent: true}`. So an agent *can* force a re-read of a single entity. Verified attributes for `'register-entity'`: `{destructive: false, readOnly: false, idempotent: false}`, input `{locationUrl}`, output `{locationId}`, body validates the URL then calls `catalog.addLocation()`. The dossier's substantive conclusion survives intact: **none of the four writes entity content.** An agent can point at YAML, unpoint it, or ask for a re-read. It cannot assert anything. |
| "No first-party Terraform, Pulumi or CloudFormation reader in core; populating Resources from real infrastructure means writing a custom EntityProvider" | **Too strong, and this is the correction that matters.** `plugins/catalog-backend-module-aws` lives *in the main Backstage repo* and ships `AwsOrganizationCloudAccountProcessor`, which "can be used to ingest cloud accounts as `Resource` kind entities", plus `AwsEKSClusterProcessor` and `AwsS3EntityProvider`. More importantly, AWS itself maintains `awslabs/backstage-plugins-for-aws`, whose **AWS Config Catalog Module** (`@aws/aws-config-catalog-module-for-backstage`) "implements an entity provider to ingest AWS resources in to the Backstage catalog" from an **AWS Config aggregator**, with a required `resourceTypes` filter, tag filters, JSONata field transforms, and an option to **generate entity names as a hash of the ARN**. That is a genuine live cloud-inventory importer, maintained by the cloud vendor, shipping today. Revise the dossier's "infrastructure is named, not understood" down to: *infrastructure nodes can be imported at real grain with real identifiers; infrastructure **edges** still cannot.* |
| Terraform | **No state reader exists that creates entities, and the ecosystem flows the other way.** The community `terraform-provider-backstage` manages the Backstage catalog *from* Terraform — and tellingly, its only writable resource is a **catalog Location**, which independently confirms the write ceiling from a second direction. Community tfstate plugins render Terraform outputs on an entity page and explicitly do not create entities. |
| `relationFields[]` shape `{selector:{path}, relation, ...}` | **Drifted.** On current `master`, `CatalogModelKind.relationFields[]` is `{path, relation, defaultKind?, defaultNamespace?: 'inherit'\|'default', allowedKinds?}` — a flat dot-path, not a `selector` object, and it gained `allowedKinds`. The type is `CatalogModelKind`, not `CatalogModelKindDefinition`. |
| Researcher uncertain whether `createCatalogModelLayer` is wired in | **Partially resolved.** `relations.ts` itself exports `wellKnownRelationsModel = createCatalogModelLayer({...})` — i.e. the shipped seven pairs *are already expressed as a model layer* in the same file that exports the raw constants. The registry is therefore consumed, not dead code. I still found no documented extension point by which an integrator registers their own layer with a running catalog backend. Treat custom relation types as "declarable in the type system, not yet installable." |

**One addition the dossier missed, and it is the sharpest thing in this document.** The life-of-an-entity docs describe the stitcher as gathering all outputs and merging them, collecting relations "no matter who produced them." That is the union-with-attribution-discarded operation. Backstage takes N independent producers who each emit the same relation, deduplicates them into one `{type, targetRef}`, and **throws the count and the identities away**. It is a working system that performs, in production, at scale, precisely the collapse that the proposition/assertion split exists to prevent. Cite it in the design doc: the corroboration count is not a theoretical nicety, it is the number Backstage computes and discards every processing loop.

## 1. Point-by-point

| Concept element | Backstage equivalent | Assessment |
| --- | --- | --- |
| **Proposition / assertion split** | **Nothing.** An entity is a document; a relation is `{type, targetRef}` with `additionalProperties: false`. There is no row representing "someone said this." | Categorical absence. The stitcher unions relations from all producers and discards provenance (§0). |
| **Content-addressed edge fingerprint** | **Nothing for edges.** Entity identity is `kind:namespace/name` — a *semantic*, human-chosen, mutable string. There is an internal entity hash used to decide whether stitching is needed, not to address edges. | Backstage's semantic identity is a design the concept explicitly rejected (opaque UUID + read-time canonicalization) and rejected correctly: renaming a Backstage component breaks every ref that points at it, because the ref *is* the name. |
| **Polarity / refutation** | **Nothing — and worse, contradiction is structurally unrepresentable.** Processors mutate in sequence; `catalog.processorOptions.<name>.priority` (default 20, lower runs earlier) decides who wins. Two authorities disagreeing produce one value and no trace. The sole exception is `CatalogProcessorErrorResult` → `entity.status.items`, which surfaces *malformed* input, never *conflicting valid* input. | No equivalent. This is the concept's single largest differentiator over the entire IDP category. |
| **Corroboration as a count** | **Anti-equivalent.** See §0 — the count is computed and destroyed. | Direct external validation of the split. |
| **Bi-temporal validity** | **Nothing.** No `createdAt`, `updatedAt`, `validFrom`, `validTo` anywhere in the public entity shape. `final_entities.last_updated_at` exists internally and is not exposed. No entity history, no instance versioning, no `as_of` query (open issue #5834). `etag` is optimistic concurrency, not a timeline. | No equivalent, and no adjacent machinery. Asking "what did we believe last quarter" is unanswerable in Backstage by construction. |
| **Scope sweeps (closed-world snapshot)** | **Real, and their version is better than the concept's within its scope.** `EntityProviderMutation` has a `full` arm: an authoritative replacement of that provider's entire set, keyed by a stable provider name. There is no `updated` arm — updates are expressed as `added`, which is a nice simplification. Orphaning is the sweep's consequence: an entity losing all parents gets `backstage.io/orphan: 'true'` and is deleted by default (`catalog.orphanStrategy: keep` to retain). | **Steal the atomicity.** Their sweep is a transactional set-replacement enforced by the provider; the concept's is a tag-then-expire pass that can half-complete if the importer crashes. Their weakness: `full` is all-or-nothing per provider, so one provider cannot own two independent scopes — which is exactly why the concept's `scope_key` is the right generalisation. |
| **Predicate cardinality (functional predicates)** | **Implicit and accidental.** `spec.owner` is a single string, so re-processing overwrites it; `spec.dependsOn` is an array, so it is set-valued. Cardinality is a consequence of JSON Schema shape, never a declared property of a predicate. | Partial by accident. The concept's explicit `functional` flag is strictly better because it survives a predicate being asserted by two different sources at different times, which schema shape cannot express. |
| **Trust score** | **Nothing.** No confidence, no score, no tier, no last-verified field. A stale entity is byte-identical in the API response to a fresh one. | No equivalent. Note the adversarial reading: Backstage has run at Spotify-and-thousands-of-orgs scale for six years and never found it necessary to ship a confidence number. That is weak evidence that trust scoring is not what makes a catalog useful — consistent with the project's own stated worry #3. |
| **anchor_integrity** | **Nothing.** `backstage.io/source-location` points at a directory URL, never a commit, never a line range. Nothing checks whether it still resolves. | No equivalent. Backstage does not attach evidence to claims at all, so there is nothing to anchor. |
| **Entity resolution: strong identifiers** | **Partial, and one piece is genuinely good.** Core identity is the semantic ref. But annotations act as an informal strong-identifier table: `github.com/project-slug`, `gitlab.com/user-id`, `backstage.io/kubernetes-id`, `sonarqube.org/project-key`, `vault.io/secrets-path`, LDAP/Entra ID attributes. And the AWS Config module can **derive the entity name from a hash of the ARN** — a real, opaque, strong-identifier-derived id. | The annotation namespace convention (`<authority-domain>/<key>`) is the best naming idea in Backstage and maps one-to-one onto `entity_identifier(authority, value)`. **Steal the namespace convention verbatim.** But annotations carry no uniqueness constraint — two entities may claim the same `github.com/project-slug` and nothing objects. |
| **Weak aliases, merge/distinct tables, read-time canonicalization** | **Nothing.** No alias table, no merge log, no negative-evidence table, no read-time indirection. Two YAML files describing the same service produce two unrelated entities forever. | No equivalent. Flip side: because Backstage never guesses, it never over-merges. Its failure mode is silent duplication, which is visible; the concept's risk is silent over-merge, which is not. |
| **`env` as a first-class discriminator** | **Nothing typed.** `spec.lifecycle` (`production`/`experimental`) is a maturity label, not a deployment environment, and `metadata.labels` can hold `env: prod` as an uninterpreted string. Namespaces could be abused for it. | No equivalent. Remains one of the concept's sharpest and least-copied edges. |
| **Call-site grain, derive service edges** | **Nothing, by explicit design.** No symbols, no functions, no ASTs, no call graphs, no diffs. The finest grain is the repo-level entity. The catalog is *declared*, not *observed*: it records that someone wrote `consumesApis: [notifications-api]`, not that any code calls it. Drift between declaration and reality is invisible. | No equivalent, and the docs own it: the catalog is "intended to capture human mental models... rather than an exhaustive inventory" and "should not be considered the ultimate source of truth... use the Backstage Catalog as a caching mechanism." |
| **Accept-then-normalize write path (202 <150ms, never 400 on unknown predicate)** | **The exact opposite philosophy, enforced at every layer.** There is no write endpoint. The ingestion path is: commit YAML → wait for the processing interval → schema validation → processor chain → stitch. Unknown `spec` fields are tolerated by default, which is the one shared instinct; unknown *kinds* are rejected unless a processor implements `validateEntityKind`. Latency from write to visibility is a poll cycle, not 150ms. | No equivalent. The concept's write path is its clearest product-level advantage over the entire IDP category, and it is a direct consequence of the audience: Backstage's writer is a human opening a PR, who can tolerate a 400 and a review cycle. An agent cannot. |
| **Multi-hop typed traversal / path templates** | **Nothing. This is the quiet dealbreaker.** The API returns relations **one hop** from an entity. `GetEntityAncestryByName` walks the *location/processing* ancestry (which location emitted which entity), not the relation graph. `by-query` predicates (`$all`, `$any`, `$not`, `$exists`, `$in`, `$hasPrefix`, `$contains`, `fullTextFilter`) filter a flat entity list — they do not join across relations. There is no recursive query, no depth cap, no edge-type whitelist, no path ranking, no `as_of`. No first-party GraphQL (the old plugin is deprecated; Frontside's `@relation` directive is the community answer). | **No equivalent.** A four-hop answer requires four sequential HTTP round trips orchestrated by the caller, with the caller supplying the traversal logic, the edge-type policy and the ranking. Backstage stores a graph and exposes an entity list. |
| **Embeddings never drive traversal** | **Convergent by omission.** Backstage Search (Elasticsearch/OpenSearch/Lunr) is keyword-based and indexes catalog entities, TechDocs and Stack Overflow as flat documents. There is no vector index in core and no embedding-based retrieval in the catalog path. | Weak convergence — they never tried it, so it is not evidence either way. Sourcegraph's *retreat* from embeddings is the stronger citation. |
| **Fact source: agent-asserted observations** | **Structurally blocked.** Verified: four MCP write actions, none of which author content (§0). The `AiResource` kind is AI-*adjacent*, not agent-written: it catalogues skills and rules that agents *consume*, and the README is explicit that content is not in the entity — "the source file is referenced via the standard `backstage.io/source-location` annotation." The catalog holds the card, not the knowledge. | No equivalent. Backstage's AI story is *feeding* agents, not *recording* them. |
| **Fact source: static analysis** | **Effectively none in core** since v1.55 removed `CodeOwnersProcessor` and `AnnotateScmSlugEntityProcessor` to community modules. Discovery providers *find* `catalog-info.yaml` files; they do not analyse code. | No equivalent. |
| **Fact source: running systems** | **Partial and better than the dossier allowed (§0).** AWS Config module ingests real cloud resources as entities with ARN-derived names; core ships AWS Organizations/EKS/S3 processors; 18 integrations including Datadog, Harness, Keycloak, LDAP, Okta, Entra ID. The Kubernetes plugin is the counter-example: "designed around the needs of service owners, not cluster admins," it fetches live objects per entity via `backstage.io/kubernetes-id` and **does not create catalog entities** — live infra is rendered, never stored. | **The closest Backstage gets to the concept, and it stops at nodes.** AWS Config gives you a `Resource` per RDS instance and ElastiCache cluster. It cannot tell you that Service C *reads from* that cluster, because that edge exists in code and in runtime traffic, not in AWS Config. Importing nodes is the easy half. |
| **Fact source: human-authored** | **Best-in-class and the whole point of the product.** YAML in-repo, reviewed via PR, org-wide discovery with glob `catalogPath`, branch/topic/visibility/archived filters, webhook-driven refresh on `github.push`/`github.repository`. | Strictly better than what the concept will build for human authoring. The concept should not try to compete here. |
| **Verification agent that can refute** | **Nothing to refute with.** Processors can emit errors that block replacement, which is validation, not verification. `refresh-catalog-entity` over MCP lets an agent force a re-read — the trigger half of a verification loop with no place to record a finding. | No equivalent. |
| **Secrets: record location, never value** | **Convergent and already named.** `vault.io/secrets-path` is exactly the "location of a secret, never its value" pattern, shipped as a well-known annotation. | **Steal the precedent and the name.** Being able to say "this is the Backstage pattern too" is worth real credibility in the `access` path template. |

## 2. The motivating query, walked concretely

**Question:** "Where does the list of notifications in Client A come from?" then "How do I connect to that database?"
**Required path:** Client A (repo 1) → calls → Service C (repo 3) → reads_from → Redis cache E → falls_back_to → Postgres → provisioned_by → Terraform (repo 4).

**What you would have to do.**

1. **Set-up.** Scaffold a Backstage app, deploy backend + Postgres, configure a `GithubEntityProvider` (or GitLab) with `organization` and `catalogPath: /catalog-info.yaml`, enable webhook ingestion. This is days, not hours, and it is a service you now operate.
2. **Repo 1 and repo 3.** Author `catalog-info.yaml` for Client A and Service C. Author an `API` entity `notifications-api`. Set `Component: client-a` `spec.consumesApis: [notifications-api]` and `Component: service-c` `spec.providesApis: [notifications-api]`. **Hop 1 now works** — and it works *well*, org-wide, which is genuinely Backstage's strongest axis. Cost: a human wrote it, and it is a declaration, not an observation.
3. **Hop 2 — Service C → Redis cache E.** Author a `Resource: redis-notif-prod`, add `service-c.spec.dependsOn: [resource:redis-notif-prod]`. Better: install the AWS Config catalog module, filter `resourceTypes` to ElastiCache, and let the real cluster arrive as a `Resource` with an ARN-hash name. **But the edge does not arrive with it.** AWS Config knows the cluster exists; it does not know who reads it. Someone hand-writes `dependsOn`. And the relation that lands is `dependsOn` — **not `reads_from`**. Backstage has seven relation types and none of them is a data-access verb. Every semantic distinction in the motivating path collapses into `dependsOn`.
4. **Hop 3 — `falls_back_to`.** This is where it breaks structurally, not just practically. `falls_back_to` is a claim *about* the relationship between the cache read and the Postgres read — it needs a proposition as a subject. A Backstage relation is `{type, targetRef}` with `additionalProperties: false`: **it cannot carry a qualifier, a condition, an order, or a reference to another relation.** The best available encoding is two sibling `dependsOn` edges from Service C — to Redis and to Postgres — which is *lossy in exactly the way that produces a wrong answer*. The graph now says Service C depends on both, with nothing recording that one is a fallback for the other. `ttl_seconds: 60` and `key_pattern: "notif:*"` have nowhere to live except free-text `metadata.description` or an untyped `label`.
5. **Hop 4 — `provisioned_by` → Terraform.** No entity kind represents a Terraform module or address. `Location` is a pointer to catalog data, not to infrastructure code. The honest encodings are a `metadata.links[]` entry (untyped, unqueryable) or a hand-written `annotation`. Community tfstate plugins render outputs on the entity page and create no entities. There is no `provisioned_by` relation and no way to declare one today (the model-layer registry could declare the *type*, with no documented way to install it).
6. **"How do I connect to that database?"** `vault.io/secrets-path` is the right shape and gives you the credential *location*. The endpoint AWS actually assigned could arrive via AWS Config. The VPN/bastion requirement lives in a TechDocs page if someone wrote it. Realistically: partial, via annotations and prose, with no guarantee it is current.
7. **Actually traversing it.** Even with every entity hand-authored perfectly, **Backstage will not walk this path for you.** Four hops is four sequential `GET /entities/by-name/...` calls, with your code reading `relations[]`, filtering by type, and deciding where to go next. There is no depth cap because there is no recursion; there is no trust cut because there is no trust; there is no `as_of` because there is no time. The catalog UI renders a relations graph for humans; the API does not expose a path query. You would be writing the concept's traversal engine anyway — on top of a store that has already discarded the qualifiers, the polarity, the evidence and the provenance you needed.

**Verdict.** Backstage answers **hop 1 well**, hop 2 as an untyped `dependsOn` if a human writes it, hop 3 **not at all** (structurally — the relation shape forbids it), hop 4 only as an untyped link, and hop 5 partially. And once the migration happens — Redis → Memcached — the stale `dependsOn` persists until a human edits the YAML, with nothing in the API to signal doubt. The one thing Backstage does better than a cold-start Living AI Knowledge instance is **hop 1 at org scale with no per-repo work beyond one YAML file** — and that advantage evaporates the instant the question needs a verb other than "depends on."

## 3. Threat assessment

**Threat level: low.**

*Distance to the concept.* Backstage would need: an entity-write API (absent by deliberate architecture — "what it exposes are final entities... not the raw originally ingested entity data"); relation properties (`additionalProperties: false` is a breaking schema change across every plugin); relation provenance (the stitcher's union explicitly discards it); temporality (open since issue #5834, unshipped for years); a recursive traversal API (no first-party GraphQL; the deprecated plugin was abandoned); confidence and refutation (no precedent anywhere in the model); and code-grain observation (nothing in six years points there). That is a rewrite of the catalog's core, not a feature.

*Structural brakes.* Backstage is a **framework**, not a product — every breaking change to `catalog-model` must be absorbed by thousands of self-hosted forks and hundreds of community plugins. The CNCF governance and the release-train cadence make a core data-model rewrite close to impossible. The v1.55 changelog shows the actual direction of travel: *removing* deprecated processors, moving them to community modules, tidying UI render props. That is a maturing framework, not one about to grow an assertion store.

*Incentive.* Real but pointed elsewhere. The 2026 AI work — `AiResource`, MCP Actions, published skills, `API` with `spec.type: mcp-server` — is uniformly about **making the catalog legible to agents**, never about letting agents write to it. That is a coherent and probably correct product bet for them, and it is the *opposite* bet from the concept's. Spotify Portal's AI Knowledge Assistant is RAG-over-the-catalog, which is precisely the "plausible but disconnected facts" failure mode the concept was designed against.

*The realistic partial threat.* Someone writes an `EntityProvider` that ingests agent-asserted facts and projects them into `dependsOn` relations. That closes maybe 20% of the value — the declared cross-repo edges — while inheriting every limitation above (no verbs, no qualifiers, no polarity, no time, no traversal). Watch for exactly one thing: a documented extension point that registers a custom `CatalogModelLayer` with the running backend. If custom relation *types* become installable, the category's ceiling rises meaningfully. It still would not give relations properties.

*What they have that the concept does not:* org-wide discovery across five code hosts with webhook freshness, CNCF distribution and a Spotify-scale reference deployment, 18 integrations, an installed base already holding a hand-curated ownership graph, and a live MCP server in agent configs today.

## 4. What to steal

1. **The annotation namespace convention: `<authority-domain>/<key>`.** `github.com/project-slug`, `gitlab.com/user-id`, `vault.io/secrets-path`, `sonarqube.org/project-key`. Adopt it verbatim for `entity_identifier.authority` — it is self-documenting, collision-free without a registry, and instantly familiar to anyone who has used Backstage or Kubernetes. Also adopt their reservation rule: "the `backstage.io` apiVersion space is reserved" → reserve one namespace for your own core predicates and identifiers, so third-party importers cannot squat them.
2. **`vault.io/secrets-path` as prior art for the `access` template.** The "record the location, never the value" pattern already has a canonical spelling in this ecosystem. Use the same shape, cite the precedent, and put it in the docs as a stated invariant rather than a policy.
3. **ARN-hash entity naming, from the AWS Config module.** Deriving an opaque, stable name from a strong identifier is the exact operation `entity_identifier` should perform on ingest. Also steal its guardrails: a **required** `resourceTypes` filter and tag filters, because the module's own README warns that AWS Config tracks enough resources to wreck both ingestion and usability. Your importers need the same "you must narrow this" default, or the fact-density risk inverts into a fact-flood.
4. **JSONata field-transform expressions in the importer config.** The AWS Config module lets an operator remap arbitrary payload fields into entity fields declaratively, without a code change or redeploy. This is a strong answer to "every new cloud resource type needs a new importer" — and it is a far cheaper extension point than Backstage's own "write TypeScript and redeploy the backend."
5. **`EntityProviderMutation`'s `full`/`delta` shape — including the absence of an `updated` arm.** `{type:'full', entities[]}` | `{type:'delta', added[], removed[]}`, keyed by a **stable, unique provider name**, with "updates are expressed as `added`." That is exactly the right API for your scope-sweep ingest endpoint, and collapsing update-into-add removes a whole class of importer bugs. Make the sweep transactional (stage, then swap) so a crashed importer cannot half-expire a scope.
6. **Orphan detection as a distinct signal from deletion.** Backstage marks `backstage.io/orphan: 'true'` and then deletes by default, with `orphanStrategy: keep` as an escape hatch. An entity whose every supporting assertion has expired is not the same as an entity that was refuted — surface the distinction, keep the row, and make the sweep policy named and configurable per scope rather than a constant.
7. **`entity.status.items` as a visible processing-error channel.** Every entity carries its own ingest errors in-band, and an errored entity is *not replaced*. Give propositions a status channel for unresolved predicates, failed anchor checks and pending merge candidates, readable on the same GET as the fact. Agents need to see why a fact is suspect without a second endpoint.
8. **`etag` optimistic concurrency.** Cheap, well-understood, and gives multi-writer safety without locks — relevant the moment the verification agent and an ingest run touch the same proposition.
9. **The `by-query` predicate language.** `$all`/`$any`/`$not`/`$exists`/`$in`/`$hasPrefix`/`$contains` plus `fullTextFilter{term, fields}`, `orderFields`, and cursor paging. It is a good, JSON-native, injection-safe filter DSL that agents emit reliably. Use it for the *anchor-selection* and entity-listing endpoints; keep traversal on typed path templates.
10. **Action attributes `{readOnly, idempotent, destructive}` with stated defaults.** "An action is assumed to be non-idempotent and not read-only" unless declared; `destructive` defaults true unless `readOnly`. When the MCP shim lands, declare these on every tool — it is what lets a host auto-approve reads and gate writes, and the default-to-dangerous choice is the right one.
11. **`catalog.get-catalog-model-description`** — an MCP tool returning markdown describing all registered kinds, annotations, labels, tags and relations. Ship the equivalent: one tool that returns your live predicate vocabulary, entity types and path templates, so an agent discovers the schema from the running instance instead of hardcoding it. This is the cheapest possible mitigation for the unknown-predicate problem.
12. **Negative lesson to internalise.** `AiResource` stores the *card*, not the *knowledge* — "the actual content of skills and rules is not stored in the entity spec." That is the catalog instinct: point at things, do not hold them. Your product is the inverse bet. Be explicit in the design doc about why, because reviewers from this world will assume you got it wrong.

## 5. Build on it, or compete?

**Build on it: no, and the reason is a single line of schema.** A Backstage relation is `{type, targetRef}` with `additionalProperties: false`, drawn from a closed set of seven pairs, derived rather than authored, with no create/update entity endpoint. Every core element of the concept — polarity, confidence, evidence, bi-temporal validity, scope_key, asserted_by, identifying qualifiers — is a property *of an edge*, and Backstage edges cannot carry properties. You would be storing your entire data model in a side table keyed by entity ref, using Backstage purely as a node registry, while paying for: a Node backend you must operate, a poll-based ingestion loop, a mandatory YAML-in-Git write path, semantic (mutable, collision-prone) entity ids, and a plugin API on a release train that breaks quarterly. The concept's write-path SLO — 202 in under 150ms — is unreachable through an architecture whose documented ingestion latency is a processing interval. And even then you would still write the traversal engine yourself, because Backstage has none.

**Data source: yes, and a good one — with one specific caution.** This is the right frame. Backstage is a **human-authored ownership and system-decomposition importer**, and it produces exactly the fact class the concept is weakest at: intentional, org-scale, cross-repo structure that no static analyser can derive and no single-repo agent session can see. Concretely:

- Poll `POST /entities/by-query` with cursor paging and ingest with `method='human'` and `scope_key='backstage:<instance>'`, sweeping each run — Backstage's own `full` semantics make this a clean closed world.
- **Strong identifiers come free and are the real prize.** `github.com/project-slug`, `gitlab.com/user-id`, `backstage.io/kubernetes-id`, ARNs via the AWS Config module. A Backstage import is one of the few sources that can resolve a code entity and an infrastructure entity to the same canonical id *without guessing* — which is the direct mitigation for risk #2 (entity resolution) in the concept's own register.
- Map relations conservatively: `ownedBy` → `owned_by`, `partOf` → `part_of`, `providesApi`/`consumesApi` → `provides_endpoint`/`calls`. **Do not** map `dependsOn` to anything specific — it is a lossy union of several real verbs, and importing it as `depends_on` with `method='human'` and modest confidence is honest; importing it as `reads_from` would poison the graph.
- `backstage.io/source-location` and `managed-by-location` become evidence records. `backstage.io/orphan: 'true'` is a ready-made expiry signal.
- **The caution, and it is real.** Backstage facts are *declared*, not *observed* — the docs themselves say the catalog is a mental model and a cache, not a source of truth. A large Backstage import will out-produce your agents immediately and make the graph look full while being made almost entirely of one low-grain fact class. That is risk #1 in the project's own register, arriving through the front door. Import it, tag it `method='human'`, give it a correspondingly modest base trust, and treat every imported `dependsOn` as a **candidate for the verification agent to confirm or refute** — which, pleasingly, is a job only this product can do, and the single clearest demonstration of why it should exist.

**Positioning.** Backstage answers "what exists and who owns it," authored by humans, one hop at a time. The concept answers "how does it actually work right now, and how do we know," asserted by agents and importers, across many hops, with the receipts. They are complements with a narrow declared-topology overlap. The overlap is real but shallow — call it a fifth of the surface, and the *easy* fifth.
