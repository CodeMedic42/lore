| `_` system blueprints, protected | **Confirmed** — `/v1/blueprints/system/{identifier}/structure` exists as a dedicated read-only endpoint. |
| Ocean has 50 integrations in-tree; remote MCP server is closed source | **Confirmed via GitHub API.** `remote-mcp-server` contains `.github`, `README.md`, `server.json` and nothing else. |
| "Ontology" is a writing-style guide | **Confirmed verbatim.** The page says *"In Port, your data model is more than a schema - it is an ontology"* and then instructs: *"Write descriptions as if explaining to a new team member who has no context"*, *"The `title` you give a relation is the semantic label of that edge — it is how agents understand the connection"*, *"Choosing a property type is not just a validation decision — it is a semantic declaration."* There are no classes, no inheritance, no axioms, no inference. The ontology is **prose in a `description` field that an LLM reads at query time.** |
| Catalog auto-discovery limits: 500 most recent entities per related blueprint, 100-char property truncation, no BYO-LLM | **Confirmed verbatim.** Added detail: *"Suggested entities persist until they are approved or declined"*, and the docs **do not** mention confidence scores, provenance for suggestions, or relation inference. Auto-discovery suggests **entities**, not edges. |
| MCP tool list | **Confirmed and slightly expanded.** Live docs add `get_action_permissions`, `test_integration_mapping` (listed as a write tool), `list_plugins`/`upsert_plugin` requiring **Port admin**, not merely Builder. |
| *"Agents that connect using an organization machine token bypass static role, user, and team checks by default"* | **Could not verify.** Fetched `port-mcp-server/overview`, `token-based-authentication`, and `dynamic-permissions`; none contain this sentence in the currently-served HTML. The docs tree was reorganised (`/ai-interfaces/` → `/agent-management/`) and this may be a stale quote from the old tree. **Treat as unverified.** It does not change any conclusion below. |
| 64 documented integrations vs "100+" marketed | **Not re-verified.** Low stakes. |

**One addition the dossier missed, and it is the most important structural fact in this comparison.** Port's write path has **no unknown-key tolerance**. `POST /v1/blueprints/{bp}/entities` validates the body against the blueprint's JSON Schema; an unknown property or a relation to a non-existent blueprint is a validation failure, and `validation_only=true` exists precisely so callers can pre-flight it. There is a `create_missing_related_entities` escape hatch for *entities*, but there is no `create_missing_blueprints` and no "store the raw key and map it later". **Port is a schema-first store that rejects at the door.** Your concept is a schema-last store that accepts everything and normalises asynchronously. That single axis explains almost every difference that follows.

## 1. Point-by-point against the concept

| Concept element | Port equivalent | Assessment |
| --- | --- | --- |
| **Proposition / assertion split** | **Nothing.** An entity has `properties` and `relations`. A relation is a value on the subject entity: `{"reads_from": "redis-prod"}`. There is no row anywhere that represents *someone saying* that. The closest artefact is an audit-log record, which is an operational log of an HTTP call, not a first-class, queryable, joinable claim. | **No equivalent, and it is categorical.** You cannot express "two sources agree" in Port's data model. You can only express "the current value is X" plus a log you must separately query to find out how it got there. This is the single largest gap and the entire reason your concept is not already shipped. |
| **Content-addressed edge fingerprint** | **Nothing.** Edges have no identity. A relation is a key on an entity; its "identity" is `(subject entity id, relation identifier)`. Two writers asserting the same edge produce one value, not two corroborating rows. | No equivalent. Note the corollary: because edges have no identity, **nothing about an edge can ever be the subject of another statement.** Your "propositions about propositions" mechanism has no analogue and no path to one without a schema redesign. |
| **Identifying vs descriptive qualifiers** | **Nothing, and structurally blocked.** Relations carry no properties. A qualifier like `key_pattern: "notif:*"` must live on one of the two endpoint entities, where it is ambiguous (which of the three caches does this pattern belong to?), or force you to reify the edge as its own blueprint. | No equivalent. Reification is *possible* by hand — create a `cache_read` blueprint with relations to service and cache plus a `key_pattern` property — but Port gives you no help: no fingerprint, no dedup, no "this edge already exists" semantics. | **Corroboration as a count** | **Partial, and weaker than it first looks — `union`.** Multi-source ingestion is a genuine, thought-through multi-writer mechanism: each writer owns a namespaced slice, `null` clears a slice, UI edits land under `user:{userId}`. It is set-union with per-writer ownership, which is real engineering. | **But it collapses to a set, not a count, and the count is unreadable.** The spec says the property *"returns the combination of all slices, with each value appearing once"* — deduplicated. Three sources agreeing is indistinguishable from one source asserting. And since no read endpoint exposes slices, you cannot reconstruct the count even if you wanted to. **Your approach is strictly better and the gap is not close.** Worse: `union` on relations **requires `many: true`**, so the exact edges you care about — `service -> reads_from -> cache`, which is naturally `many:false` in most models — cannot use it at all. So Port can answer "what was this service's `tier` last quarter" and cannot answer "what did the notification data path look like last quarter." Your bi-temporal model is better for the problem you have. Note also: **no stated retention policy** for the history store was found; `last3Years` is a preset ceiling, not a guarantee. |
| **Scope sweeps (closed-world snapshot)** | **Partial, at coarse grain, and deliberately defanged.** Full resync reconciliation is exactly the right shape: *"The deletion process ensures that entities that are no longer present in the data source are removed."* Scope is roughly `(integration, kind)`. `entityDeletionThreshold` is a 0/1 switch: *"Set to `0` to disable automatic deletion or `1` to enable it."* | **It deletes entities, never edges-as-facts, and Port has deliberately made it hard to fire.** The documented behaviour when you remove a kind from a mapping: *"When you remove a resource type from your integration mapping or decommission an integration, the associated entities in Port are not automatically deleted."* Followed by a manual three-step ritual with a warning — *"Always remove the mapping **before** deleting entities. If you delete entities first, the next integration resync will recreate them."* — and the note that deletion is irreversible. **The sweep is destructive, not an expiry.** Your `valid_to = run_start` retains the fact and marks it historical, so a later query with `as_of` still sees it and a human can audit why it vanished. Port's sweep is `DELETE`. **Yours is better, and by a wide margin, precisely because yours is non-destructive.** Steal the scoping idea (§4); do not steal the semantics. |

So `many:false` *does* auto-expire the prior value. | **But it expires by destruction with no record in the entity, and there is no notion of a non-functional predicate accumulating assertions.** `many:true` accumulates values with no expiry at all — the Memcached migration problem in its purest form: the old `redis` target simply stays in the array forever unless a resync deletes it. ## 2. The motivating query

**"Where does the list of notifications in Client A come from?" — spanning four repos into Terraform-provisioned infrastructure.**

### What you would have to build

Port has no opinion about software architecture, so you author the ontology yourself. Minimum viable model:

1. **Blueprints.** `service`, `repository`, `endpoint`, `cache`, `database`, `terraform_resource`, `environment`. Port ships `service`, `environment`, `workload`, `deployment`, `organization` as editable defaults; the rest you write.
2. **Relations.** `service -> calls -> endpoint`; `endpoint -> served_by -> service`; `service -> reads_from -> cache`; `cache -> falls_back_to -> database`; `database -> provisioned_by -> terraform_resource`. Each is `{title, description, target, required, many}` — no properties, so `key_pattern: "notif:*"` and `ttl_seconds: 60` have to go on the `cache` entity (wrong — they are properties of *this service's use of* the cache, not of the cache) or you reify a `cache_access` blueprint and hand-manage its identity.
3. **Populate the infra half.** This is where Port shines and you would genuinely be done in a day. AWS v3 gives you `AWS::ElastiCache::CacheCluster` and `AWS::RDS::DBInstance` as real entities with ARNs. The TFC integration gives you Workspace, Run, and **State File** — and JQ over the state file can produce the `provisioned_by` edge. GitLab v2 gives you every repo, branch, pipeline and MR. **`Redis cache E -> falls back to -> Postgres -> provisioned_by -> Terraform` is achievable with configuration alone.**
4. **Populate the code half. This is where it breaks.** There is nothing in Port that can determine that Client A calls Service C, that Service C reads Redis, or that it falls back to Postgres. No code index, no AST, no symbol graph, explicitly **no file-content inspection**. Your options:
   - **Hand-author** every `calls` and `reads_from` edge in `port.yml` files, committed per repo. This is Backstage's `dependsOn` under a different name, with the same rot problem: it is true the day it is written and silently false thereafter.
   - **Write a custom Ocean integration** that runs your own static analysis and pushes entities. This is you building the thing, with Port as the storage layer — which is a legitimate strategy (§5) but is not Port answering the query.
   - **Have an agent write the edges via MCP `upsert_entity`.** Works today. And the moment two agents disagree about Service C's cache, the second overwrites the first with no record in the entity, because `reads_from` is naturally `many: false` and **`union` requires `many: true`.**
5. **Query it.** You cannot express this as one traversal. `relatedTo` requires a named `blueprint`, so you must already know each hop's type; `maxHops` needs an explicit ordered `path` array of relation identifiers. In practice you write a **fixed path query** — `["calls","served_by","reads_from","falls_back_to","provisioned_by"]` — which is not a template over a *class* of questions but a hardcoded route for exactly one question shape. Any service that reaches Postgres by a different route (direct, via a queue, via a second service) returns nothing. To cover the space you enumerate routes.
6. **Narrate it.** `POST /v1/ai/invoke` over MCP does this well and returns SSE with `tool_call`/`tool_result`/`done`. Defaults are 200 LLM calls/min, 500k tokens/min, 500 invocations/month on Port-managed LLMs; BYO-LLM is supported.

### Where it actually breaks down

- **The code half has no source.** Everything from `Client A -> calls -> Service C` through `reads_from -> Redis` is unpopulated unless a human or your own analyser writes it. This is 60% of the motivating query.
- **Entity resolution between halves.** The Redis your code reads is `redis://notif-cache.prod:6379`. The Redis in Port is `arn:aws:elasticache:eu-west-1:123:cluster/notif-cache-prod`. **Nothing joins them.** You solve it with a JQ mapping expression that reconstructs one from the other, which is the fragile string-munging your entity-resolution design exists to eliminate. Get it slightly wrong and the traversal returns nothing, with no diagnostic.
- **Staleness is invisible.** When Service C migrates to Memcached, the `reads_from -> redis` relation persists until something explicitly overwrites it. Nothing on the entity says how old it is or who wrote it; you must go to `/v1/audit-log`. And for an agent-written edge there is no resync to sweep it.
- **Question two — "how do I connect to that database?"** — Port answers this *well*, and better than you will initially, because this is its home turf: an RDS entity with endpoint and port, an org secret, and a self-service workflow that grants access with approval. The security posture is also better than the naive version of yours: Port's answer is *"trigger this workflow"*, not *"here is the value"*. **Steal that framing directly.**

**Verdict:** Port can answer the infrastructure two-thirds of the chain out of the box and none of the code two-thirds without you building the analyser. It cannot answer the whole chain as one traversal and cannot tell you how much of the answer to trust.

## 3. Threat assessment

**Threat level: high.** Higher than the code-intelligence vendors, because Port already owns the half of the problem that is *expensive infrastructure work* and is explicitly marching toward agents.

**What they already have that you do not:** a production multi-tenant typed graph with a mutable schema; a hosted MCP server with per-tool governance; 50 open-source integrations spanning every cloud, Terraform and Kubernetes; bidirectional Terraform ownership of the catalog itself; RBAC, SSO, SCIM, audit, EU/US regions; distribution into platform teams; and an executive narrative — "Context Lake", "Agentic SDLC platform" — that is *already the story you would tell*.

**What they would have to build:**
- The proposition/assertion split. This is a **schema rewrite of the core product**, not a feature. Every entity, every mirror property, every calculation property, every scorecard rule, every JQ mapping and the entire Terraform provider assume `entity.relations[name] = value`. Introducing "a relation is a set of timestamped, signed, refutable claims" breaks all of it.
- Refutation and polarity — meaningless without the above.
- Bi-temporal validity and as-of traversal — the history store exists but is per-entity, per-property, and does not compose with search.
- Entity merge/alias/read-time canonicalization — this one they have real incentive for, because duplicate entities across integrations is a known, customer-facing pain. **Expect them to ship some form of entity merging. Do not expect it to be read-time-canonical or non-destructive.**
- Code-level grain. Nothing adjacent. They would acquire or partner.
- Trust scoring. No sign of intent.

**Do they have the incentive?** Partly, and the part they have is not the part you care about. Port sells seats to platform engineering. Their buyer wants a correct catalog, a golden path, and scorecards that make teams comply. That buyer does not ask for epistemics — they ask *"why does this service show the wrong owner"*, whose answer is better integrations, not confidence intervals. Port's agent investment is aimed at **letting agents execute governed workflows**, which is an actions story, not a memory story. The gravitational pull of their roadmap is toward more integrations, more workflow nodes, more agent management — all orthogonal to your differentiation.

**The realistic threat is not that Port builds your product. It is that Port ships "good enough" and owns the category name.** They are already calling the catalog a "Context Lake" and a "unified engineering knowledge layer", while their own docs concede it is *"not a separate feature, but rather the powerful result of Port's core capabilities working together"* — i.e. the catalog, renamed. If a platform team already pays for Port, the conversation you must win is *"we already have a graph our agents can write to"*, and winning it requires a demo where Port's answer is confidently wrong and yours says *disputed, last verified 40 days ago, evidence path deleted at HEAD*. **That demo is your entire go-to-market. Build it before you build anything else.**

**Time for Port to close the gap on the epistemic layer: 12–24 months and a core-model rewrite they have no customer pull for.** Time for them to close the *narrative* gap: they already have.

## 4. What to steal

**1. Search-query-as-identifier — steal this outright, it is the best idea in the product.** Instead of demanding an id, accept a resolution predicate inline. Live schema (`def-5`): `{combinator: and|or, rules: [{property, operator: =|in|contains|containsAny, value} | <nested def-5>]}`. Make your `POST /v1/observations` accept this in `subject`/`object`, and make it your resolution-ladder DSL. **Improve on it where they are weak:** they require exactly one match and fail otherwise; you should mint a provisional entity and record the ambiguity as an assertion, never failing the write.

**2. `create_missing_related_entities` as a write flag.** A boolean on the write that says "mint anything I reference that does not exist." Exactly your provisional-entity rung, expressed as an API affordance rather than hidden behaviour. Name it the same.

**3. `validation_only` as a first-class dry-run param.** Your write path never rejects, so this is not about validation — it is about *explaining resolution*. `POST /v1/observations?dry_run=true` returning "here is how I would resolve each anchor, here is the fingerprint I would compute, here is the existing proposition I would corroborate" is the debugging tool you will otherwise build badly in month four.

**4. `union` source keys — steal the shape, fix the read.** `{"<sourceKey>": [values]}` where the writer owns only its slice, `null` clears it, UI edits land under `user:{userId}`, and the key pattern is `^[A-Za-z0-9._:@/-]{1,128}$`. That pattern is a good `scope_key` format — adopt it. Then fix their fatal flaw: **always expose per-source decomposition on read.** Your `GET /v1/propositions/{fp}/assertions` is exactly the endpoint they are missing, and their omission is your demo.

**5. `run_id` and `node_run_identifier` on the write.** Port lets a write declare which run produced it, which is `scope_key` + `session_id` with a better name. Borrow both, and borrow `ocean_info_event_type` / `ocean_info_resync_id`, which distinguish "this write came from a full resync" from "this came from a live event" — **exactly the signal your scope sweep needs to decide whether a run is closed-world.** Make it an explicit enum on ingest: `snapshot | incremental | event | ad_hoc`. Only `snapshot` arms a sweep.

**6. `x-read-only-mode: 1` removing write tools from the advertised list.** Gate capability at tool *advertisement*, not at call time. A model that never sees a write tool cannot hallucinate a write; a model that sees one and gets 403 will retry, rationalise, and burn tokens. Adopt this in your MCP shim from day one, plus `x-allowed-actions-to-run`-style allowlisting for anything that mutates.

**7. `delete_dependents` and `entityDeletionThreshold`.** A deliberate safety valve on cascading removal. Your sweep is non-destructive, but you still need a circuit breaker: if a sweep would expire more than N% of a scope's assertions, **halt and flag rather than proceed.** Port learned this the hard way enough to ship a config flag for it.

**8. The "access" answer shape.** Port's answer to "how do I connect" is *invoke this approval-gated workflow*, not *here is the secret*. Your `access` path template should return a **capability** — the location of the secret, plus the action that grants it — never a value. Their model is the safe pattern and it directly addresses your fourth named risk.

**9. Mirror properties as a read-time denormalisation concept.** `{"path": "system.domain.domain_members"}` — a dot-chain of relation identifiers terminating in a property, flattened onto the entity. This is a materialised path lookup with a nice authoring syntax, and it is a good model for caching your derived service-level edges from call-site grain. Note their gotcha to avoid: mirror properties **cannot be used in search-query-as-identifier resolution**, because the denormalisation is not guaranteed fresh. Yours will hit the same wall; design for it now.

**10. `207 Multi-Status` on batch writes.** Partial success with per-item status. Your batch observation endpoint will need this and it is cheaper to design in than retrofit.

**11. The rename endpoints.** `PATCH /v1/blueprints/{bp}/properties/{id}/rename`, `.../relations/{id}/rename`, `.../mirror/{id}/rename` — dedicated non-destructive identifier changes. Your predicate vocabulary will churn as you async-map raw predicates. A first-class `predicate rename` operation that rewrites the mapping without touching assertion rows is worth having on day one.

**12. `direction: upstream | downstream` as the traversal primitive naming.** Clearer than `in`/`out` or `forward`/`reverse` for this domain. Use it.

## 5. Build on it, or compete?

### Could you build on Port?

**Technically yes; strategically no.** You could model `proposition` and `assertion` as blueprints, with an assertion relating to its proposition and both to entity blueprints. Then:

- Every assertion becomes an **entity write** against a 200-burst-per-5-minutes rate limit on single upserts, or batches of 20. You would be paying SaaS entity-count pricing (10k free / 50k / 250k / 1M+) for rows that are, by design, high-cardinality and append-only. **Your data model's central premise — many assertions per proposition — is the worst possible fit for a per-entity-priced catalog.**
- Your fingerprint becomes a Port `identifier` string, so dedup works, but **you get no help from the platform** — no content addressing, no corroboration counting.
- Your recursive CTE becomes a sequence of round-tripped `relatedTo` calls, each requiring a named target blueprint, each network-bound. A depth-6 traversal is six HTTP calls against a rate-limited API.
- Bi-temporality, trust cuts and `as_of` you implement as properties Port cannot index for your access patterns, filtered client-side.
- You inherit last-writer-wins on every `many:false` relation, a closed-source store you cannot profile, and an entity cap.

You would be using a governed catalog as a triple store. **PostgreSQL with a recursive CTE is better at this in every dimension, and your architecture decision to use it is correct.**

### Is Port better understood as a data source?

**Yes — and it is the single most valuable importer available to you.** This directly attacks your first and largest named risk (fact density: agents only restate what is in the repo in front of them).

Concretely:

- **`POST /v1/entities/search` with `{"combinator":"and","rules":[]}` is a full catalog dump**, blueprint by blueprint, paginated, over a plain bearer token. Import every entity as an entity in your graph and every relation as a **proposition with a single assertion of `method='telemetry'`** (or a fifth method, `catalog_import`), `asserted_by='port'`, evidence `{system: 'port', blueprint, entity_identifier}`.
- **`scope_key` per (blueprint, integration)**, so each import run is a closed-world snapshot and your scope sweep expires what Port has dropped. Port's own resync semantics guarantee the closed-world property you need.
- **Its identifiers are your strong identifiers, free.** AWS ARNs, Terraform addresses, GitLab project paths, K8s resource ids — Port has already done the tedious work of pulling them from source systems into one place with stable keys. **That is exactly your `entity_identifier (authority, value)` table, pre-populated, and it means you inherit the infrastructure half of the motivating query without writing a single cloud integration.**
- **`GET /v1/audit-log` with `includes: ["diff", "context"]` is a change feed.** Poll it, and every `UPDATE` with a relation diff becomes an assertion with `valid_from = audit timestamp` and an expiry of the prior one. **This is where you extract the temporal signal Port does not itself model** — Port stores current state plus a log; you can reconstruct a bi-temporal history from the log that Port cannot query. That is a genuinely asymmetric advantage: *you can answer questions about their data that they cannot.*
- **`properties-history` for the entities you care most about**, backfilling valid-time intervals.
- **Their `union` slices are lost on read** — so import at the *writer* grain where you can: the audit log's `origin` field tells you which integration wrote a value, letting you mint a distinct assertion per source and **recover the corroboration count Port throws away.**
- **Do not import scorecard rule-results wholesale** — 5M-entity caps and 24-hour sync lags mean this data is stale by construction. Import scorecard *definitions* as human-authored propositions about policy, not the results.

Port fills your graph with the infrastructure and ownership layer. Your agents and static analysis fill the code layer Port structurally cannot reach. **The seam between them — joining `redis://notif-cache.prod:6379` in source to `arn:aws:elasticache:...:cluster/notif-cache-prod` in Port — is precisely the entity-resolution problem your design exists to solve, and it is the thing neither Port nor any code-intelligence vendor does.** That seam is the product.

### Positioning

Do not position against Port. Position **downstream of it**: *"Port knows what you have. We know how it connects, who said so, and whether it is still true."* If a prospect has Port, you import it on day one and are immediately more useful than a cold start. If they do not, you have lost an importer, not a category.

**The one thing to watch:** if Port ships entity merging with alias tables and per-source read attribution — both of which are natural, customer-demanded extensions of `union` and their duplicate-entity pain — the gap narrows materially without them ever touching propositions. Check their changelog quarterly for those two words.
