# Pulumi Insights / Pulumi Cloud vs. Living AI Knowledge — feature-by-feature comparison

**Comparison date:** 2026-09-24
**Scope:** Pulumi Cloud "Discovery & governance" (formerly Pulumi Insights): Discovery scanning, Resource/Property Search, the Context API graph (public preview, launched 2026-08-26), and Neo.
**Verification status:** primary sources consulted directly. The live OpenAPI document was downloaded from `https://api.pulumi.com/api/openapi/pulumi-spec.json` (OpenAPI 3.0.3, **479 paths, 819 schemas** — both confirmed by parsing) and every schema quotation below is taken from it, not from marketing pages. Docs pages verified: `/docs/discovery-governance/concepts/context-api/`, `/docs/discovery-governance/guides/context-api/`, `/docs/discovery-governance/guides/search-resources/`, `/blog/pulumi-context-api/`, `/pricing/`. `GET /api/insights/graph/schema` was attempted live and returns **401** without a token, so the concrete `fieldValues` and numeric `limits` still come from the docs limits table, not the live endpoint.

**Three additions the dossier missed, all load-bearing:**

1. **There is a natural-language → query endpoint.** `GET /api/orgs/{orgName}/search/resources/parse`, `operationId: GetNaturalLanguageQuery`: *"converts a natural language query into a structured Pulumi search query using AI. For example, converts 'show me all S3 buckets in production' into a proper search syntax."* Gated `402 "AI assist feature requires Enterprise subscription"`. This is a shipped, narrow version of the concept's *NL question → anchors* step. It resolves anchors only; it does not choose a path template.

2. **Discovery reads ARE version-addressable.** `InsightsResourceIdentifier` carries an optional `version` with the comment *"If nil, the latest version is used."* Combined with `ListResourceVersions` and per-version edge listing, the Discovery *storage* layer is a real, if primitive, system-time archive. It is simply not wired to the Context API or to search. That is a shipped-but-unexposed capability, which is a different and more dangerous thing than an absent one.

3. **`ResourceResult.fingerprint` exists** — *"A fingerprint uniquely identifying this resource's state."* This is a content hash over a **node's state**, not over an **edge**, so it is not the concept's proposition fingerprint. But it means Pulumi has already built the "content-address the observed thing so re-observation dedupes" machinery on the node side.

## 2. The motivating query, walked through concretely

> *"Where does the list of notifications in Client A come from?"*
> `Client A (repo 1) → calls → Service C (repo 3) → reads_from → Redis cache E → falls_back_to → Postgres (AWS) → provisioned_by → Terraform (repo 4)`

**Verdict: Pulumi answers roughly one and a half of the five hops, and the query is not expressible in its language even if every node existed.**

**Setup required.** Create a Pulumi org (Pro at $400/mo minimum, possibly Enterprise at $2,000/mo — gating is contradictory across their own sources). Create an ESC environment holding AWS OIDC credentials with `ReadOnlyAccess`. Create an Insights account per AWS account, set `scanSchedule`, wait for a scan. Optionally deploy all four repos with Pulumi so their stacks land in the graph with `vcs:repo` tags auto-populated.

**Hop 1 — Client A `calls` Service C. Fails.** There is no repository node and no application-call edge. If Client A is a frontend, it is not a resource and has no node at all. The **only** way this hop exists is if repo 1's *Pulumi stack* consumes repo 3's stack output (an API Gateway URL, say), in which case `consumes_outputs_of` fires — **stack→stack**, not client→service, and only when the call is wired through IaC rather than a hardcoded URL, a service-discovery lookup, or config injected at runtime. In practice this hop is present in a minority of real estates.

**Hop 2 — Service C `reads_from` Redis cache E. Partial.** If Service C is deployed as an ECS service / Lambda / k8s Deployment, it is a node. If its task definition takes the ElastiCache primary endpoint from the cluster resource's output, `reference` fires with `basis: declared` — which is a *good* fact. If the endpoint arrives via ESC, SSM, a config map or a literal string, nothing fires except possibly `inferred_reference`, which the docs themselves label *"a lead to verify."* And the edge, when it exists, asserts only *"the program recorded this dependency."* It does not say **read**.

**Hop 3 — `falls_back_to` Postgres. Structurally impossible.** Both Redis and RDS appear as `reference` targets of the same service. Nothing distinguishes *primary* from *fallback*. The distinction is precisely what your descriptive qualifiers and proposition-subject-of-proposition exist to carry; Pulumi's model flattens it to two identical edges. An agent reading the Context API response cannot recover the semantics and will guess.

**Hop 4 — Postgres `provisioned_by` Terraform repo 4. Partial, and lossy in the way that matters.** The scan finds the RDS instance and sets `managed: 'Terraform'`. That is the **tool**, not the repo, not the module, not the address. There is no `terraform_address` field anywhere in the schema, no repo node, and the Pulumi MCP resource-search tool's own prompt admits: *"Resources may not have a repository url."* You get "something Terraform-shaped owns this" and stop. Your concept's `tf_address` strong identifier is exactly the missing link.

**Hop 5 — "How do I connect to that database?" Genuinely good, and dangerous.** Property search over the RDS resource's outputs returns `.endpoint`, `.port`, `.dbName`, `.vpcSecurityGroupIds` — richer and more current than an LLM-asserted graph would be, because it comes from live cloud state on a 12h cadence. Then Neo will open the ESC environment holding the password without asking. That is the behaviour your risk #4 is trying to avoid, shipped as a default.

**The query-language wall, independent of data.** Even granting every node, `traverse[]` permits **4 steps** over **6 fixed edge types**. The path you want is 5 typed hops of 5 *different* semantic kinds. The best available expression is "walk `reference` with `depth{min:1,max:6}` from Service C" — which returns an undifferentiated dependency blob, then hands the LLM 500 evidence `paths[]` to guess over. That is a materially worse answer than a single typed path, and it is the strongest argument for your typed schema that exists in this dossier.

## 3. Threat assessment

**Threat level: LOW to the concept as specified; MEDIUM-HIGH to the infrastructure leg of it specifically.**

**What Pulumi would have to build to ship your concept:**

1. **A user-extensible type system.** Their vocabulary is *"published, not extended"* and enforced with 400s. Adding `calls`, `reads_from`, `falls_back_to` means either hardcoding them (feasible, narrow) or building a schema registry (a direct reversal of a stated design principle).
2. **An assertion layer.** Author, method, polarity, confidence, evidence, corroboration count. Nothing in 819 schemas prefigures it. Their graph's single-author assumption is baked into collapse-not-reconcile.
3. **Bi-temporality in the query engine.** They have system-time storage in Discovery and explicitly do not expose history in the graph. Wiring versions into a traversal engine with a 20,000-node budget is expensive and they have shown no appetite.
4. **Code entities and a code indexer.** Repo, file, symbol, endpoint, call site — and something that produces them. They have *zero* of this. Neo clones repos at task time and persists nothing.
5. **An arbitrary-edge ingest API.** `UpsertResources` writes *resource state* and derives edges from a `dependencies[]` array of resource references. You cannot post a typed edge between two arbitrary nodes.

**Do they have the incentive?** Partly, and less than it looks. Pulumi monetises **resource-hours** (managed $0.00025/hr, discovered from $0.000025/hr) plus Neo tokens ($3/M). Every one of those meters counts *cloud resources*. A graph of application semantics across repos does not increment any meter they own. Their stated roadmap — *"Pulumi ESC environments, teams and roles, cloud accounts, and service catalog concepts from Pulumi IDP"* — is entirely **more Pulumi Cloud objects as nodes**. Not one roadmap item is a code entity.

**Do they have the adjacent pieces?** Alarmingly many: a working typed-graph engine with the best result-honesty metadata in the market; agentless multi-cloud scanners with org-wide bulk onboarding; ESC for credentials; a full agent runtime (tasks, SSE streams, approval modes, BYOK, usage caps); a hosted MCP server at `mcp.ai.pulumi.com`; 16 published agent skills distributed into Claude Code, Cursor, Copilot, Codex and Gemini; and a preview **Custom Agents** capability (`agentDefinitionId`, *"A preview capability, gated per organization"*). If they decide to add a `service` node type and a `resource → repository` edge, they are halfway into your infra leg in a quarter.

**The realistic forecast.** Pulumi will keep getting better at "what infrastructure exists, what depends on what, what breaks if I change this" — and will likely eat that leg of your graph outright within a year. They will not build an assertion model, because their data has one author and admitting a second one would force them to reconcile disagreements they currently collapse. **Plan for their infra graph to become excellent and to be something you consume.**

**What this says about your own risk register:**

- **Risk 1 (fact density) — Pulumi is the strongest evidence *for* the fear.** Their graph is 100% importer-derived, 0% agent-asserted, and it is a real, sellable product. That is proof an importer-only graph has value. It is *also* proof that an importer-only graph **cannot answer your motivating query** — §2 shows it failing at hops 1 and 3. Your defensible ground is exactly the edges importers cannot produce. That is a narrow and honest claim; make it your thesis rather than "we also import infra."
- **Risk 3 (trust may be theater) — Pulumi votes against your trust formula.** They shipped no confidence score at all, and wrote into their own enum comment that `basis` *"classifies production, not trustworthiness rank."* Their answer to epistemic honesty is metadata in the wire format, not arithmetic. Given you have zero labelled data for an AUC measurement, shipping `basis`-style classification plus result-fidelity metadata first — and treating the four-factor score as a strictly separate experiment — is the lower-risk sequencing.
- **Risk 4 (secrets) — Pulumi demonstrates the failure mode publicly.** Their own docs say read-only doesn't cover cloud accounts and that Neo opens ESC environments unprompted. Your rule is both safer and differentiating.

## 4. What to steal — concretely

**4.1 `meta` on every traversal response. Copy the field names.** Return `{resultMode: "exact"|"truncated", visibility: "complete"|"trimmed", schemaVersion: "<date>"}`. Your traversal clips for *more* reasons than theirs — depth cap, edge-type whitelist, trust cut, `as_of` horizon, fanout — so extend it: `meta.clippedBy: ["depth"|"trust_cut"|"fanout"|"as_of"|"scope"]`. Today a path that got cut by a trust threshold is indistinguishable from a path that does not exist. That is the same bug they refuse to ship.

**4.2 Copy their absence warning into your API docs, near-verbatim.** *"Do not use a result to prove absence until you have read every page, every page reports `meta.resultMode: 'exact'`, and, for a traversal, every page reports `meta.visibility: 'complete'`."* For you the third condition is `meta.clippedBy` being empty. An agent that mistakes "no path found under trust ≥ 0.6" for "no path exists" will confidently tell a user a service is unused.

**4.3 Selector limits vs result limits — adopt the distinction as an API rule.** A selector limit is validated and **rejects** before the query runs; a result limit **clips** and marks the result truncated. Pick which of your caps is which, document it, and never let a cap do both.

**4.4 `basis` on the edge TYPE, not the edge.** Your `method` lives on the assertion, which is correct, but a consumer must aggregate assertions to decide how to treat an edge. Add a derived, type-level classification on the traversal response — `derived_basis: "declared" | "inferred" | "observed"` — with a documented handling rule per value, and Pulumi's framing: it classifies *production*, not rank. Copy the phrase *"a lead to confirm, not a fact"* into the response for inferred edges.

**4.5 A self-describing schema endpoint that serves markdown to agents.** `GET /api/insights/graph/schema` returns JSON, and with `Accept: text/markdown` returns an **agent primer** that the CLI caches for 24h (`--refresh-spec`). Build `GET /v1/schema` returning predicates with cardinality, entity types with their strong-identifier authorities, path templates, and traversal limits — JSON for clients, markdown for the LLM. This is how you keep "never 400 on an unknown predicate" from degenerating into a garbage vocabulary: **accept anything at the door, but publish what you know so agents converge on it.** Copy their three-way field split too: `selectableFields` / `projectableFields` / `groupByFields`, with the explicit note that they are *different sets*.

**4.6 `identity` as a published string per node type, and publish both spellings.** Their schema carries a prose `identity` field and documents a trap: a stack's returned id is `stack:<org>/<project>/<stack>` but a selector must use the org-free `project/stack`, *"and the field lists cannot say so: they name fields, never formats."* You will have exactly this problem — canonical UUID in responses, human strings in writes. Publish the read spelling and the write spelling of every identifier type, explicitly.

**4.7 Constrained human override.** `statusOverride` *"must be Migrated"* — the human may override the machine in exactly one direction, the one where being wrong is cheap. Worth a hard think for your human-authored assertions: unrestricted human refutation is a griefing and error surface, and "humans may confirm freely, refute only with evidence" may be the right default.

**4.8 `frontier[]` per node and `paths` as explicit evidence.** Every returned node carries the names of the traversal frontiers that selected it; every traverse step takes an `alias`. Your path templates should name each hop (`anchor`, `service`, `cache`, `store`, `provisioner`) and return the alias on each node. LLM narration gets dramatically easier when the model is told *which role* a node plays rather than inferring it from position. And copy the honest caveat: *"A path is evidence of one route, not an enumeration of every route."*

**4.9 `fieldsUnavailable` per node.** A boolean meaning *this node came back thin, do not trust projections off it*. Your analogue: a node reached by traversal whose entity is provisional / unresolved / merge-candidate. Surface it per node, in the response, not in a log.

**4.10 Scope bounds anchors, not traversal.** *"Bounds where the anchor set is selected. Traversal may walk beyond the scope."* Write this as a test in your traversal suite. The whole point of the product is edges that leave the repo you started in.

**4.11 Hierarchical scope keys.** Insights account names are `/`-separated and naming a parent selects every descendant (`acct` selects `acct/us-east-1`). Free hierarchy, no graph query, trivial in SQL with `LIKE 'prefix/%'`. Make `scope_key` path-shaped from day one — `gitlab:group/project@main` — and you get sub-scope sweeps for nothing.

**4.12 Cumulative edge pagination.** *"every edge whose higher-id endpoint first appears on this page… process pages cumulatively"*, with the caveat *"A drain over changing data may not be complete."* A precise, honest contract for paginating a graph that is being written to concurrently. You have a multi-writer store; you will need exactly this.

## 5. Build on it, or compete?

**Build on it: no.** It fails on four independent grounds, any one of which is fatal. (1) **Read-only** — there is no way to store a proposition; `UpsertResources` takes resource state, not typed edges between arbitrary nodes. (2) **Closed schema** — the vocabulary is published, not extended, and enforced with 400s; you cannot add `calls` or `falls_back_to`. (3) **No temporality in the query layer** — the docs say it cannot answer historical queries, so `as_of` is unimplementable on top. (4) **Hosted SaaS at $400–$2,000/mo with contradictory gating**, against a concept whose stated audience is "single user locally first."

**Data source: yes, and this is the strongest integration candidate in the whole competitive set.** Pulumi's Context API maps onto your assertion model almost field-for-field, and it is one of the very few sources that can produce *declared, machine-derived, infrastructure* edges at scale.

A concrete importer design:

- **Strong identifiers.** Register authorities `pulumi_urn`, `insights_urn`, `pulumi_stack` (`org/project/stack`) and `insights_account`. The AWS ARN usually sits inside `ResourceResult.properties` or `id`, giving you a second strong id and the join to any other cloud source you add later.
- **Edge mapping.** `reference` → `depends_on` with `method=code_derived`; `inferred_reference` → `depends_on` with `method=llm_inferred`-equivalent and a lower base, honouring *"a lead to verify"*; `parent` → `contained_by`; `provided_by` → `provisioned_by` (mark it single-hop); `in_stack` → `deployed_in`; `consumes_outputs_of` → `depends_on` at stack grain.
- **Assertion fields.** `asserted_by = "pulumi:insights"`, `method = telemetry` for scan-discovered and `code_derived` for IaC-declared, `evidence = [{urn, account, stack, schemaVersion, scanId}]`, `valid_from = scan start`.
- **Scope sweep — the killer fit.** A scan of an Insights account *is* a closed-world snapshot, which is exactly the premise of your sweep mechanism. `scope_key = pulumi:insights:<org>/<account>`, `valid_to = scan_start` for anything not re-asserted. This is the cleanest sweep source you will ever get, because Pulumi already guarantees the closed world.
- **Result honesty.** Refuse to sweep when `meta.resultMode` is `truncated` or `meta.visibility` is `trimmed` — an incomplete read would expire live edges. Their metadata makes this decidable, which is the practical payoff of §4.1.
- **`env`.** Derive it from the stack name, the account hierarchy and the `Environment`/`env` resource tag — and refuse to merge across it, as designed.

**What the importer still will not give you**, and therefore what you must produce yourself: any node in repos 1–4, any `calls` / `reads_from` / `falls_back_to` edge, the Terraform *address* behind `managed: 'Terraform'`, and every hop the motivating query actually turns on. **That is the honest boundary: Pulumi is the best available supplier of the last two hops and supplies nothing for the first three.**

**One caveat on cost and reach.** The Context API is Pro/Enterprise-gated ($400/mo at best), and Discovery's own `sourceCount` and `managed` fields are the only cross-tool signal. For a single developer on a laptop — your stated day-one audience — this integration is out of reach. It is a team-tier feature. Build the importer behind the repository interface, ship it as optional, and do not let the data model bend around it.

## 6. Bottom line

Pulumi Insights is **the best infrastructure graph on the market and not a knowledge graph at all.** It models what infrastructure exists and what depends on what, derived from a single trusted author, with no notion of anyone *claiming* anything. Every one of your differentiating mechanisms — proposition/assertion split, polarity, bi-temporality in query, predicate cardinality, weak aliases and read-time canonicalization, call-site grain, typed application-semantic edges — is absent, and most are absent by deliberate design rather than backlog.

Two things should genuinely worry you. First, their **query-fidelity metadata is better than yours and you have nothing comparable** — `resultMode`, `visibility`, `frontier[]`, `fieldsUnavailable`, `basis`, capped evidence `paths`, and a written prohibition on using a clipped result to prove absence. That is epistemic honesty encoded in the wire format, and it costs a week to adopt. Second, they looked at ranked trust and **chose a two-value type-level classifier with an explicit note that it is not a rank** — which is a real, informed vote against your four-factor score, from a team shipping this problem in production.

The gap that is genuinely yours is the one §2 exposes: five typed hops, of which Pulumi can express roughly one and a half, in a query language of six fixed edge types. Hold that ground, consume their infra graph rather than rebuilding it, and steal their response metadata this week.
