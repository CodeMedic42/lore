**The new finding, and it matters most for §5.** Every search surface Greptile exposes to an external agent is **case-insensitive substring matching — literally grep — not semantic search.** From the live tool descriptions:

- `search_knowledge_base`: *"Search one repository's current knowledge base for a **case-insensitive substring**"*, with hard budgets — *"a 200-document limit, a 2,097,152-character read budget checked between reads, a 524,288-character searchable prefix per document, and a 15-second work budget"*, and an 80 KiB serialized response cap.
- `search_custom_context`: *"Search visible custom-context bodies by **case-insensitive substring**"*. `%` and `_` are SQL wildcards — this is a `LIKE` query with the escaping leaked into the API contract.
- `search_greptile_comments`: *"Search Greptile-generated review comments by **case-insensitive body substring**"*, and *"There is no offset"*.

So the docstring-embedding vector index that is Greptile's entire retrieval story is **purely internal**. Externally, you get `ILIKE '%term%'` over synthesized markdown with a 15-second budget. Any plan that treats Greptile as a semantic retrieval backend for your graph is mistaken about what the API does.

### Where Greptile is genuinely ahead

Three things, and they are all epistemics rather than data model:

1. **Incompleteness signalling.** Typed `truncationReason`, `contentTruncated`, `documentsFailed`, `documentsScanned`, `characterCount` vs returned `content`, and the doctrine that absence is not proof. Your concept has no notion of a partial read at all.
2. **Untrusted-content labelling with a stated threat model.** *"Anyone who can land a commit can influence it."* Your graph is 100% synthesized content and you have not designed for this.
3. **Deliberate non-oracle error design.** Repository-not-found is made indistinguishable across "unknown id", "another organization's" and "outside your team's repositories" — *"All three look identical by design."* Your multi-writer team model will need exactly this.

## 2. The motivating query

**Question:** *"Where does the list of notifications in Client A come from?"* — expecting `Client A → calls → Service C → reads_from → Redis cache E → falls back to → Postgres in AWS → provisioned_by → Terraform module`.

**Verdict: Greptile cannot answer this, and no amount of configuration makes it able to.** Not "would answer it poorly" — there is no surface through which the question can be asked.

Walk it concretely.

**Step 1 — pick an API.** Your options are the MCP server (21 tools) or the undocumented CLI-facing REST API. The retired `POST /v2/query` — the one endpoint that took a natural-language question about a codebase — returns `unknown_endpoint`. There is no "ask a question" verb left in the product. The closest is `search_knowledge_base`, which is substring search over synthesized markdown for **one repository**, capped at 15 seconds of work and 80 KiB of response.

**Step 2 — get the four repos in scope.** Create a Repo Cluster containing Client A, Service C, the shared-types repo and the Terraform repo. This requires org-admin. Constraints that bite immediately: the cluster must stay under **20 GB total**; members must be *"on the same SCM host as the primary repository, and accessible with the same credentials"* (if your Terraform lives in a separate GitLab group under different credentials, or on a different host entirely, this path is closed before it starts); and crucially, **a cluster does nothing until a PR is opened**. It is context assembly for a review. It creates no index, no queryable artifact, nothing you can read.

**Step 3 — try to query across them.** You cannot. `search_knowledge_base` takes a single `namespaceId` and the tool text instructs you to *"call it once per repository from `list_knowledge_bases`"*. So you fan out four substring searches for `notification`, get back up to 3 snippets per document from a 200-document, 512 K-character-prefix scan of each repo's synthesized docs, and receive four disconnected result sets with `untrustedContent: true`. Nothing joins them. There is no identifier shared between "the `notifications` endpoint in Client A's KB" and "the `notif:*` key pattern in Service C's KB" — no entity, no edge, just two strings that happen to contain the same substring. **The join is the entire product you are building, and it is exactly what is missing.** You would be reimplementing entity resolution in the client against grep output.

**Step 4 — the infrastructure hop.** Even if you hand-resolved steps 1–3, `reads_from → Redis cache E` has nowhere to live. Greptile's entity vocabulary is organization, team, user, repository, repo cluster, PR, code review, comment, custom context, KB document, finding, analytics bucket. That is the complete, fixed ontology: **no user-defined entity types, no user-defined relations, no properties, no blueprint layer.** There is no row that can be a Redis instance. `metadata` on a custom context is an open JSON blob, but the docs and tool descriptions are clear it is returned as an opaque object — it is not indexed and not queryable as structured data, so stuffing a graph into it buys you nothing you could not get from a text file.

**Step 5 — the Terraform hop and `provisioned_by`.** Terraform is just `.tf` text in a repo. Greptile would index it as files and variables. Nothing connects `aws_elasticache_cluster.notifications` to the Redis client instantiation in Service C, because connecting two things across repos requires an edge type Greptile has no table for.

**Step 6 — "How do I connect to that database?"** This is where the closest thing to an answer exists and it is an anti-answer. The CLI **actively withholds** sensitive files before upload — dotenv, `*.pem`, `*.key`, `*.p12`, `id_rsa`, `.npmrc`, and diffs containing recognizable AWS/GitHub/Slack/Google/Stripe/Anthropic/OpenAI key patterns. Greptile's considered position is that this material should not enter the system. **Adopt that list verbatim as a deny-filter on your ingest path** — it is a free, battle-tested answer to your risk #4, and your `access` path template's "return the location, never the value" rule needs a mechanical enforcement layer underneath it, not just a policy.

**The one thing Greptile would do well here.** If Client A's KB happened to contain a synthesized paragraph naming Service C, `search_knowledge_base` would find it, and the *prose* might be accurate — the docstring pipeline is good. You would get one plausible hop as unstructured text, with no way to verify it, no provenance beyond "Greptile synthesized this from the repo at some unspecified time", and no way to ask for the next hop. That is a search result, not a traversal.

## 3. Threat assessment

**Threat level: low.** Not because Greptile is weak — it is a well-engineered, commercially healthy product — but because closing this gap requires them to become a different company.

**What they'd have to build.** Essentially the whole concept. A typed proposition/assertion store (they have no fact table at all); an extensible entity model with user-defined types (they have a fixed twelve-type vocabulary with no extension hatch); entity resolution across repo *and* infrastructure identifier authorities (they resolve repos by tuple equality and nothing else); a traversal API with recursive CTEs (they have substring search with a 15-second budget); bi-temporal storage (they explicitly cannot return a historical version); a persistent cross-repo index (they clone-per-review and throw it away); and ingestion from cloud APIs and OTel (TREX produces runtime signal and deletes it).

**What they already have that would help.** More than is comfortable. Postgres + pgvector already deployed. A code graph at call-site grain already built and already used for impact analysis. A repository-identity model that already separates opaque canonical id from mutable handle. An MCP server with mature multi-tenancy, OAuth, and unusually disciplined tool semantics. TREX — a runtime execution substrate that already touches real services. A read-only SCM integration across six hosts. An org/team/role model. If Greptile decided to do this, the infrastructure would not be the hard part.

**Do they have the incentive?** Strongly no, and the evidence is that they already had this business and exited it. The v2 query API — "ask questions about your codebase", the thing Greptile was originally known for — has been **removed**, not deprecated with a migration path. The VS Code extension is archived. The `examples` repo is a relic. The Slack "ask about your codebase" product is gone. Greptile looked at the developer-knowledge-API market, had a product in it with real adoption, and walked away to sell per-seat code review at $30/seat with credit-metered usage. Their revenue model is reviews; their benchmarks are bug-catch rates; their changelog for the last twelve months is review summaries, review engines, security agents and partner integrations. A knowledge graph produces no reviews.

**The realistic adjacent move**, if any, is that they extend the Knowledge Base into a cross-repo synthesized artifact — an architecture doc spanning a Repo Cluster rather than one repo. That would be a natural product step, would use machinery they already have, and would make a *narrative* answer to your motivating query plausible within a couple of quarters. It would still be prose, still un-queryable, still un-refutable, and still stop at the repo boundary. Watch for it; do not fear it.

**Timeline to genuine overlap:** 18+ months and a strategy change. Probability they attempt it: low.

## 4. What to steal

Concrete and ranked by value.

1. **Typed truncation reasons, wired into scope sweeps.** Copy `truncationReason ∈ {document_scan_cap, scanned_character_cap, response_character_cap, time_budget, repository_scan_cap}` onto your scan-run record, and make the sweep's closed-world assumption **conditional on a clean completion**. A sweep over a truncated scan must expire nothing. Right now your design has no way to even notice. This is a latent data-loss bug and this is the fix.
2. **`trust_reasoning` alongside `trust`.** Greptile never ships its confidence score without `confidenceReasoning`. Do the same, in structured form: `{base: 0.6, freshness: 0.9, anchor: 0.3, corroboration: 1.2, notes: "evidence file modified in abc123"}`. It converts your unproven trust hypothesis from an opaque number into the labelled dataset you need for the AUC measurement you already committed to.
3. **`untrustedContent: true` + a `notice` on every narrated response.** Your entire graph is agent-synthesized, and your read path ends with an LLM narrating retrieved text. Greptile's rationale applies to you verbatim and more strongly: *"anyone who can land a commit can influence it."* Emit the flag and the notice on every path response.
4. **The CLI's secret deny-list, verbatim.** dotenv, `*.pem`, `*.key`, `*.p12`, `id_rsa`, `.npmrc`, plus provider key-format regexes (AWS/GitHub/Slack/Google/Stripe/Anthropic/OpenAI). Apply as a hard filter on evidence text and on any free-text ingest. Give it an explicit `--include` style override with an audit record, as they do. Directly retires risk #4.
5. **Per-field merge semantics instead of a cardinality boolean.** Their config merge declares `max` / `union` / `intersect` / `strictest` per field. Generalise your functional-predicate idea to `predicate.merge_policy` with a small enum. Cardinality-1 is just `functional`.
6. **`files.json` as a fact-source primitive.** `{path, description?, scope?[]}` — register a *pointer* to an authoritative in-repo artifact rather than ingesting its content. Terraform modules, OpenAPI specs and Prisma schemas are authoritative and change constantly; a pointer resolved at read time never goes stale.
7. **Non-oracle error design.** *"The identifier is unknown, belongs to another organization, or sits outside your team's repositories. All three look identical by design."* Your multi-writer model needs this from day one; retrofitting it after you have leaked entity existence through 404-vs-403 is painful.
8. **`linkedMemory` / `linkedComments` as an API shape.** Bidirectional shallow provenance — from a stored claim to its instances, and back — with `evidenceCount` as a cheap scalar on the claim. That is your corroboration count and your assertion list, and their naming and response shape are good.
9. **The never-suppress list.** Hard-code categories that decay, sweeps and suppression may never remove — secrets locations, prod entities, anything with `method=human`. A decay mechanism with no floor eventually eats your most important facts.
10. **Async-accept wording.** *"A success response confirms the webhook accepted the request, not that analysis finished."* Put that sentence, adapted, in your `POST /v1/observations` 202 response body and in your OpenAPI description. It sets agent expectations correctly at near-zero cost.
11. **Version-pin the traversal.** Pin `as_of` once at query start so every level of the recursive CTE sees one snapshot — Greptile's KB scan pinning, applied to graph reads.
12. **Rule `id` for scoped override.** Their `{rule, id?, scope?, severity?, enabled?}` with `id` as the handle a child scope uses to disable a parent's rule is a clean pattern if you ever add scoped policy on top of facts.

## 5. Build-on vs compete, and the data-source question

**Build on it: no. This is not a close call.**

You cannot build a knowledge graph on a system that exposes no graph, no fact store, no write path for facts, no cross-repo query, no extensible schema, no update and no delete. The two writes available to you are "start a code review" and "create a free-text rule". You would be using a $30/seat/month code-review product as a bag of strings with no delete verb. There is additionally no supported API contract to build against: the documented public surface is 21 MCP tools; the wider REST surface exists only in a CLI bundle, serves no OpenAPI spec (404), appears in no documentation, has unknown rate limits and unknown stability — and the product has already demonstrated, by removing the v2 query API without a deprecation notice in either changelog, exactly how much warning you would get.

**Data source: marginal, and probably not worth the integration for a long time.**

There are four candidate feeds. Honestly assessed:

- **Knowledge Base documents** (`list_knowledge_bases` → `list_knowledge_base_documents` → `get_knowledge_base_document`). Greptile-synthesized architecture prose per repo, paths restricted to `index.md` and `docs/**.md`, with an immutable `versionId` and `characterCount`. This is the best of the four: it is real, structured-enough, per-repo architecture description that your free-text ingest endpoint was designed to eat. Ingest as `method=llm_inferred`, `asserted_by=greptile`, evidence `{repo, kb_path, versionId}` — and the `versionId` is a genuinely good `scope_key`, because it is immutable and changes exactly when the content does, giving you a clean sweep boundary for free. **Caveats that matter:** synthesis is *enabled per organization as a rollout, not by default*, so you may not have it at all; reads always follow current, so you can never re-fetch what you ingested last month to check drift; and every sentence arrives flagged `untrustedContent`. You would be pouring low-trust LLM prose into a graph whose whole premise is provenance discipline. Give it the lowest `base(method)` you have.
- **Review comments** (`search_greptile_comments`, `list_merge_request_comments`). Rich: `filePath`, `lineStart`/`lineEnd`, `severity`, `category`, `securityIssue`, `hasSuggestion`. But these are *defect claims about a diff*, not architecture claims. They populate almost none of your predicate vocabulary. Low value, and the search is substring-only with no offset.
- **Custom contexts** (`list_custom_context`). Team policy statements, which are a different modality from facts. Interesting as `method=human` assertions about conventions; not architecture.
- **TREX runtime data.** The one feed that would actually be valuable — real execution traces from real services — is not in the MCP surface at all, lives only in undocumented endpoints, and is ephemeral by design.

**Net.** Greptile is not a competitor and is a weak data source. Overlap with your concept is small and almost entirely accidental: they store things and you store things. The single sentence for the person about to spend months on this is that **Greptile already built the hardest engineering piece you need — a call-site-grain code graph over indexed repositories — and then deliberately made it invisible, because reviews sell and knowledge graphs did not.** That is simultaneously reassuring (they will not compete with you) and a warning worth sitting with (a well-funded team with the index already built looked at monetising it as queryable knowledge and chose not to).

The strongest reason to keep them in your research file is not the data. It is that Greptile has thought harder than almost anyone about the **epistemics of serving LLM-generated content to another LLM** — truncation honesty, untrusted-content labelling, non-oracle errors, never-suppress floors, confidence-with-reasoning. You are building a product where every one of those problems is more acute than it is for them, and you currently have designs for none of them.
