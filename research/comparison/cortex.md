**One thing the dossier under-sold.** AWS **tag-based auto-linking** on relationship types is real and is Cortex's actual answer to "how does a service get connected to its database". This is a deterministic, non-fuzzy, exact-match entity-resolution mechanism that happens to be **enforced by the infrastructure itself** — and it is better than anything in your resolution ladder for the infra half of the graph. ## 2. The motivating query, walked concretely

**Question:** "Where does the list of notifications in Client A come from?"
**Required path:** Client A (repo 1) → `calls` → Service C (repo 3) → `reads_from` → Redis cache E → `falls_back_to` → Postgres in AWS → `provisioned_by` → Terraform (repo 4). Then: "How do I connect to that database?"

### What you would have to build in Cortex

**Entities.** Four descriptors minimum, each a valid OpenAPI 3 document. `client-a` (type `service`), `service-c` (type `service`), `redis-cache-e` and `notifications-db` as cloud resources — the latter two ideally auto-imported by enabling Cloud Control types `AWS::ElastiCache::CacheCluster` and `AWS::RDS::DBInstance`, which gets you `{type, region, accountId, identifier}` identity for free. Repo 4 has no representation; at best you create a `repository` entity and hand-link it.

**Hop 1 — `calls`.** Easy and idiomatic. `x-cortex-dependency: [{tag: service-c, method: GET, path: /v1/notifications}]` in Client A's descriptor, provided Service C's descriptor declares that path under `paths`. Dependency grain is the endpoint, which is close enough. **Works.**

**Hop 2 — `reads_from` (Service C → Redis E).** Here the model forks and both branches hurt.
- *As a dependency:* possible — dependencies are explicitly *"directed towards an outgoing service or resource"*. You would either hand-author it, or let AWS dependency discovery infer it by tagging the ElastiCache cluster `service = service-c`. But a dependency is **untyped**. The edge `service-c → redis-cache-e` carries no predicate. You cannot distinguish `reads_from` from `writes_to` from `publishes_to` except by stuffing a string into `metadata`, which nothing traverses.
- *As a typed relationship:* you create a relationship type `reads-from` with `sourcesFilter{types:[service]}` and `destinationsFilter{types:[aws-elasticache]}`. Now the edge is typed — and now it lives in a **different traversal namespace** from hop 1, because dependencies and typed relationships are separate mechanisms with separate CQL accessors.

You have already lost. Hop 1 is `dependencies.out()`; hop 2 is `entity.destinations(relationshipType="reads-from")`. No single query crosses both.

**Hop 3 — `falls_back_to` (Redis E → Postgres).** This is the hop the data model cannot represent. `falls_back_to` is not a claim about Redis and Postgres; it is a claim **about the `reads_from` edge** — "when *this read* misses, fall through to *that* store." That is a proposition whose subject is a proposition, and Cortex has no edge-instance properties at all outside dependencies, let alone edges about edges. Your options are: (a) a bare `redis-cache-e → notifications-db` relationship of type `falls-back-to`, which is exactly your own bug #1 — every service touching that Redis now appears to fall back to the notifications database, with no `via_proposition` to constrain the walk; or (b) a custom-data key on `service-c` holding a JSON blob describing the fallback, which is not traversable, or (c) a `description` string on the dependency, which nothing reads. **This hop does not work.**

**Hop 4 — `provisioned_by` (Postgres → Terraform in repo 4).** **No mechanism exists.** Cortex does not ingest Terraform state, does not parse HCL, and has no Terraform-address identity. The only honest proxy is the CloudFormation-flavoured tag matching (`aws:cloudformation:stack-name`) which does not apply to Terraform, or a hand-authored relationship from the RDS entity to a `repository` entity you also hand-authored, which you must hand-maintain forever and which no sweep will ever correct. **This hop is manual fiction.**

**Hop 5 — "How do I connect to that database?"** Partially good news. The RDS entity, imported via Cloud Control, carries real AWS metadata — endpoint, port, engine version, subnet group — visible on the entity page and readable via `AWSGetAwsResources` (**cached**, not live). Bastion/VPN/secret-location knowledge has no home except custom data or a link. Cortex has `Secrets`, but those are *workspace credentials for integrations*, not a "where the credential lives" record. Your `access` template returning the **location** of a secret and never its value has no counterpart, and nothing in Cortex stops a well-meaning engineer from pasting a connection string into `x-cortex-custom-metadata`. **Half works, by accident.**

### The verdict on the query

Cortex can hold a **hand-curated, current-state, untyped-or-single-typed approximation** of hops 1, 2 and 5. It cannot express hop 3 at all, has no mechanism for hop 4, and — decisively — **cannot traverse the chain even if every edge existed**, because CQL walks one relationship type at a time and returns entities rather than paths. You would end up writing four API calls and stitching the path in application code, at which point Cortex is a key-value store with an expensive UI.

And the maintenance story is worse than the modelling story. Every hand-authored edge is un-timestamped, un-attributed, and un-refutable. When Service C migrates Redis → Memcached, the `reads-from` edge persists until a human notices, and the only systemic correction available is the daily auto-archive (which only fires if the *resource* vanishes from AWS, not if the *relationship* changed) or the next verification period, which asks a human "is this entity correct?" and takes a yes/no.

## 3. Threat assessment

**Threat level: low-to-medium.** Cortex is the most *architecturally adjacent* of the IDP competitors and the least likely to move.

**What they would have to build.** Not features — a different storage model. Specifically: (1) an assertion table with polarity, method, confidence, evidence and bi-temporal validity, which means every current-state read path in Scorecards, CQL, Data Explorer and the entity page becomes an as-of query; (2) properties and provenance on relationship instances, currently four strings; (3) a heterogeneous multi-hop path query that returns paths, which CQL's entity-scoped evaluation model does not accommodate — the `POST /api/v1/queries` result type is literally a list of `{name, tag, type, description}`; (4) code-grain evidence (repo, commit, path, line range), which requires code ingestion they do not do; (5) Terraform/IaC ingestion, which does not exist; (6) an agent-writable, never-rejecting endpoint, which directly contradicts *"YAML is the source of truth."*

**Do they have the incentive?** Weakly, and pointed elsewhere. Their 2026 marketing pivot is AI **governance, readiness and maturity** — measuring whether your org is ready for AI — plus the DRIVE framework and Eng Intelligence. That is a management-reporting motion sold per seat to platform and engineering leadership. Your product is an agent-runtime substrate with no dashboard. The buyer is different, the pricing model is different (*"per-seat model… Pricing is customized"* — an agent that writes a million assertions is not a seat), and the guarantee is different: an IDP's credibility rests on the catalog being a **curated, human-attested, authoritative** record, and admitting a firehose of un-attested agent claims into it destroys exactly the property they sell. The verification-period design is the clearest statement of their values in the whole product: only a *direct member of the owning team* may attest, there is *no global verifier role*, and machine inferences are quarantined until a human accepts them.

**Do they have adjacent pieces?** Yes, and they matter. Deep cloud/K8s/APM ingestion; ~54 integrations; Axon and Axon Relay for reaching inside customer networks without firewall holes; a user-defined typed-relationship layer with cardinality and filters; a shipped machine-inference → human-attestation pipeline; an MCP already in agent configs; Workflows that can call arbitrary HTTP with async callbacks. If they wanted to, the cheapest credible move is not building your graph — it is letting the OpEx agent or AI Chat **write custom data and custom events**, which would give them "agents annotate the catalog" headlines without touching the data model. Watch for MCP write tools and for `runWorkflow` appearing in the MCP manifest; today it is conspicuously absent.

**Most likely outcome.** Cortex stays a curated human catalog with excellent infrastructure ingestion, adds read-side AI, and never acquires provenance or refutation. You remain uncontested on the assertion model and on traversal — and permanently behind on infrastructure ingestion, which is the argument for treating them as a source (§5).

## 4. What to steal — concretely

1. **`isSingleSource` / `isSingleDestination` as declarations on the predicate type.** This is your predicate cardinality, better named and declared in the right place. Put `cardinality: functional | inverse_functional | many_to_many` on your predicate vocabulary row rather than inferring it, and expose it in the API so an agent can see it. Keep your expiry semantics — do not adopt their reject-on-violation.
2. **`sourcesFilter` / `destinationsFilter` = `{include: bool, types: [], providers: []}` as a typed domain/range on the predicate.** Two lines of schema, and it turns "unknown predicate stored raw" into "unknown predicate stored raw **and** flagged as type-violating." Cheap, high-value input to your normalisation queue and a direct attack on over-merge: a `reads_from` whose object resolves to a `repository` is almost certainly a bad resolution.
3. **`definitionLocation: SOURCE | DESTINATION | BOTH`.** Declares *which end of the edge is allowed to assert it*. For you this is an authority rule: an agent inside repo 1 may assert `calls` outbound but should not be believed about Service C's internals. Encode it and use it as a `base(method)` multiplier.
4. **The quarantine pattern for machine-inferred facts.** Ownership Recommendations do not land in the catalog; they sit as recommendations until accepted, and the guide tells you to follow a bulk accept with a verification period. Give yourself an assertion `state` of `proposed | active`, auto-promote high-corroboration `code_derived` assertions, and hold low-confidence `llm_inferred` ones out of default traversal until corroborated or human-accepted. This directly mitigates your risk #1: an importer flood cannot silently drown agent claims if they enter at different states.
5. **Dependency identity = `(caller, callee, method, path)`, with `description` + `metadata` outside identity.** Independent confirmation of your identifying/descriptive split. Also steal the **endpoint pin as an identifying qualifier** — `method` + `path` on a `calls` edge is exactly the "finest observable grain" you want, expressed as a qualifier rather than a separate node, and it collapses cleanly when you derive the service-level edge.
6. **Tag-based auto-linking as a strong identifier.** *"Cortex scans entities matching the relationship type's source and destination definitions and creates a relationship wherever tag values match."* Add `authority='aws_tag'` (and `k8s_label`, `otel_resource_attr`) to `entity_identifier`, keyed on `(tag_key, tag_value)`. This is exact-match, human-configured, and — crucially — **the tags are written by the same Terraform that creates the resource**, so the identity is maintained by the infrastructure pipeline rather than by your resolver. It is the single highest-precision cross-system identity mechanism available, and it costs you a table.
7. **Atomic whole-scope replace.** `PUT /api/v1/relationships/{relationshipTypeTag}` replaces a whole type in one call. Make your scope sweep a single transaction against a staging table so a crashed importer cannot half-expire a scope — same guarantee, without losing your validity intervals.
8. **Published refresh cadences as a contract.** "AWS dependencies sync daily 08:00 UTC; Scorecards re-evaluate every 4h" is a **staleness SLA a user can reason about**, and it is more legible than a decayed float. Surface `scope_key → last_sweep_at → expected_interval` on every path you return. If your trust score fails its AUC test, this is the fallback that still ships.
9. **Auto-archive's failure discipline: *"skipped if errors detected."*** A closed-world sweep run against a partial scan is catastrophic — it expires everything the failed scan did not reach. Make your sweep refuse to run unless the scan reports clean completion, and record that decision.
10. **Naming.** `definitions` for types, `descriptor` for the authored artefact, `tag` for the human slug versus an immutable CID, `discovered entities`, `verification period`. `x-cortex-tag` (immutable human slug) alongside an 18-char CID is precisely your "opaque UUID + human handle" pairing with better ergonomics — an 18-char CID is copy-pasteable in a way a UUID is not.
11. **Negative lesson to internalise.** `POST /api/v1/queries` returns `{name, tag, type, description}` and the docs say re-running requires the UI. A query API that returns only node identities makes path narration impossible and forces N+1 round trips. Your traversal endpoint must return the **full path with every proposition, assertion and trust input inline** — and it must be re-runnable by id.
12. **Anti-pattern to design against, explicitly.** *"all the sources are merged together and de-duplicated"* is the sentence your whole proposition/assertion split exists to avoid. Put it in your design doc verbatim as the thing you are not doing.

## 5. Build-on vs. compete vs. consume

### Could we build on Cortex?

**No, and the blocker is not a missing feature.** Five independent hard stops:

- **No per-fact provenance, anywhere.** Nothing in the data model has a place for `asserted_by`, `session_id`, `method` or `evidence[]`. You would encode assertions as JSON inside `custom-data` values or `custom-events`, immediately abandoning traversal — because neither is an edge.
- **Edge instances are four strings.** You cannot attach confidence, evidence, validity or a qualifier to a relationship. Dependencies accept `metadata`, but a dependency is untyped, so you would be re-implementing your predicate vocabulary inside an opaque JSON blob on the only edge type that has one.
- **Current-state only.** *"not suited for time-sensitive tracking"*, *"Historical Scorecard data isn't supported yet."* No `as_of`, no bi-temporality, no way to add one.
- **The write path is adversarial to agents.** `application/openapi` descriptor bodies, JSON Schema validation, cardinality rejection, and *"If a dependency has already been set through the `cortex.yaml`, the API returns an error."* Your 202-and-normalise-later ergonomics are unbuildable on top of a system whose stated invariant is that a human's YAML wins.
- **Traversal cannot express the query.** One relationship type per hop, entity-sets rather than paths, no trust cut, no `as_of`, 1000 req/min, and an async job API that returns node identities.

Cost estimate if you tried anyway: you would build your entire schema inside `custom-data` JSON, query it with JQ inside CQL, get no traversal, no dedup, no corroboration, and pay per seat. It is strictly worse than the Postgres you already have running.

### Is Cortex better understood as a data source?

**Yes — and it is one of the best importers you could plug in, for exactly the half of the graph you are weakest on.** Concretely, a `cortex_import` scope with `method='telemetry'` or `'human'`:

| Cortex read | Becomes | Notes |
| --- | --- | --- |
| `listAllEntities`, `getEntityDetails` | Entities + `entity_identifier` rows | `x-cortex-tag` → weak alias; CID → strong id `authority='cortex_cid'`; `x-cortex-infra.aws.cloudControl{type, region, accountId, identifier}` and ECS ARNs → strong id `authority='arn'`; `gitRepositories` (`gitlab:ns/project`) → `authority='gitlab_project'`; K8s `{cluster, namespace, kind, name}` → strong id. **This is a pre-resolved cross-system identity table, hand-curated by a paying customer's platform team.** It is the highest-quality input your resolution ladder will ever see, and it arrives as exact strong identifiers, not name similarity. |
| `listDependenciesForEntity` | `calls` propositions, with `method`+`path` as identifying qualifiers | Method `human` where descriptor-authored, `telemetry` where `providerType`/discovery-derived. Confidence moderate: union semantics mean you cannot tell corroboration from a single source, so import each as **one** assertion and say so. |
| `listEntityRelationships` per relationship type | Typed propositions, predicate = `relationshipTypeTag` | Map each customer-defined type into `predicate_alias` for review rather than guessing. `isSingleSource`/`isSingleDestination` → predicate cardinality, imported directly. |
| `getCustomDataForEntity` | Descriptive qualifier propositions | Source tag (YAML/API/webhook) → `method` and `asserted_by`. |
| `listVerifications`, `listVerificationsForEntity` | **Human assertions with real polarity** | Verified-correct → `polarity=true, method='human'`, `valid_from` = verification date. Verified-**incorrect** → the one genuine refutation signal Cortex produces, with a human's free-text reason as evidence. This is the highest-trust input available anywhere in the ecosystem and it is API-readable. |
| `AWSGetAwsResources`, `KubernetesGetK8sResourcesForEntity` | Infra entities + attributes for the `access` template | Cached, not live — record the cache semantics in `method`. |
| `getDeploysForEntity`, `listDeployEnvironments` | `env` discriminator values, grounded | Cortex's deploy environments are the one place `prod`/`staging` is first-class. Use them to populate your `env` field from a real source instead of string heuristics. |
| Discovered entities / auto-archive events | Sweep signals | "AWS Resource Not Detected" is a closed-world expiry signal you can act on. |

**The strategic read.** Cortex's daily 08:00 UTC AWS tag sync, its ~54 integrations and its Cloud Control importers do the work your risk #1 says agents cannot do — and they do it for infrastructure, where agents genuinely cannot see. Importing from Cortex does not make you "an importer with agent annotations"; it makes the infra half of the graph *someone else's solved problem* so your agents can spend their assertions on the part only they can observe: the **code-to-infrastructure boundary** (`reads_from`, `falls_back_to`, the key pattern, the TTL) that Cortex's model structurally cannot express. That boundary is exactly where your motivating query breaks in their product and exactly where your proposition-about-a-proposition construction earns its keep.

One caveat: Cortex is closed-source, per-seat, custom-quoted SaaS with no free tier and no published trial. You cannot develop against it without a customer. Treat the importer as a design-for, build-later adapter behind your repository interface — and note that Backstage, whose catalog model is similar in shape and open-source, is the one you can actually test against today.
