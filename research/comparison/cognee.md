## 2. The motivating query

**"Where does the list of notifications in Client A come from?" — four repos, into Terraform-provisioned AWS.**

Verdict: **no, and the blocker is structural, not a matter of configuration.**

Walk it concretely.

**Setup you would have to do.** Turn `ENABLE_BACKEND_ACCESS_CONTROL=false` — mandatory, because the default gives each `(user, dataset)` its own Kuzu/Ladybug database and graph traversal cannot cross a database file. That also turns off authentication, so this is a single-user posture only. Then `add()` all four repos into **one** dataset so enola produces one snapshot with cross-file edges — which means overriding the shipped plugin behaviour, whose whole design is one repo per dataset (`codebase-<repo>-<digest>`), and accepting the stale-node-sweep collision risk that naming exists to avoid.

**Hop 1 — Client A → Service C.** Client A calls Service C over HTTP. Enola emits a `symbol` fact for the calling function and an `ApiEndpoint` (`route`) fact for Service C's handler. It emits **no relation between them** — enola resolves relations by bare fact name within the snapshot, and `fetchNotifications` does not equal `GET /v1/notifications`. `build_code_graph_edges` skips unresolvable relations rather than guessing. **The first hop does not exist in the code graph.**

**Hop 2 — Service C → Redis E.** Better odds. Enola may emit a `storage` fact if Service C's Redis usage is recognised by an extractor, producing a `StorageResource` node linked `part_of` its module. But `StorageResource` is documented as "a table or bucket" — it is a *name in code*, not an instance. There is no `key_pattern`, no `ttl_seconds`, no identifying-qualifier concept. You get a node called `notifications` and no way to say which Redis it lives in.

**Hop 3 — Redis → Postgres fallback.** A fallback path is control flow, not a declared dependency. Enola does not emit a "falls back to" fact. This edge can only come from an LLM reading the source — which routes through `cognify`, which produces `Entity` nodes in the **semantic** graph, which is a **disjoint node population** from the code graph. An `Entity` named `Redis` and a `StorageResource` named `notifications` have no edge and no shared identity scheme. There is no mechanism that unifies them.

**Hop 4 — Postgres → Terraform.** Zero Terraform support. Your only option is to `add()` the `.tf` files as text and let the LLM extract entities from HCL. That yields `Entity` nodes with free-form relation names in the semantic graph — again disconnected from the code graph, and now subject to `consolidate_entities` merging `aws_db_instance.notifications` with anything else scoring ≥ 0.85.

**The query itself.** Assume, generously, that every hop existed. You still cannot ask it. `GRAPH_COMPLETION` returns the **top 5 embedding-scored triplets**, not a path — a four-hop chain would need four specific connected edges to all independently outrank everything else against one query embedding, which is exactly the "plausible but disconnected facts" failure your concept names. `code_query find_path` *would* return a real path — but it only sees code-graph nodes (so hops 3 and 4 are absent), it requires the caller to supply exact node names (there is no anchor-resolution stage), and it cannot reach `Entity` nodes at all.

**Where it breaks down, ranked:** (1) no cross-repo call-site resolution across a network boundary; (2) code graph and semantic graph are disjoint populations with no shared entity identity; (3) no infrastructure fact source of any kind; (4) no path-template retrieval over the semantic graph; (5) no anchor resolution feeding the one real traversal API.

**"How do I connect to that database?"** Only if someone wrote it into a doc or a `Rule`, and it would come back through `HYBRID_COMPLETION` as chunk text — with no guard against that chunk containing the password, and with the plugin having already captured every `psql` invocation from every session.

## 3. Threat assessment — **medium**

**What they would have to build:** an infrastructure fact source (cloud APIs, Terraform state, OTel) — greenfield; an entity-identity scheme that unifies the code graph and the semantic graph — architectural, touching `fact_node_id` and `Entity.identity_fields`; strong/weak identifier separation with non-destructive merging — a rewrite of `consolidate_entities` and the introduction of read-time canonicalization the storage layer has no concept of; polarity on assertions — a change to the edge model and every retriever; and actually *reading* `valid_to`, `superseded` and `contradicts` at query time, which is the cheapest item on the list and the one that most exposes the gap, because it means every retriever must learn a filtering concept none of them has.

**Do they have the adjacent pieces?** Substantially, yes, and this is the honest part. The `provenance_edge_evidence` table is the assertion sidecar. The code-graph snapshot/sweep is your scope sweep, implemented well. The truth-subspace epoch pattern is a sophisticated staleness primitive. `code_query find_path` is a real deterministic traverser. The plugin hook architecture solves fact density better than anything you have planned. The pydantic `DataPoint` subclassing model means a third party could define `TerraformResource`/`RedisInstance`/`Environment` types **today** without forking. A determined team could assemble a credible demo of your concept on Cognee in weeks.

**Do they have the incentive?** This is why the threat is medium and not high. Cognee's product identity is **agent memory** — conversations, documents, preferences, skills, session distillation. Their benchmark is BEAM, a conversational-memory benchmark. Their cloud connectors are Slack, Notion, Linear, Drive. Every one of the mechanisms above is load-bearing for chat memory and merely *adjacent* to software architecture. The code graph is a bolted-on deterministic subsystem that deliberately shares nothing with the memory graph, and the direction of travel in v1.6 (`improve`, truth subspace, session distillation, skills) is further into conversational memory, not into infrastructure. Enola is a **third-party dependency**, not their asset: they do not control the extractor roadmap, so "make enola emit cross-service HTTP edges" is not a thing they can ship.

**Your real exposure** is not Cognee deciding to compete. It is a customer saying "isn't this just Cognee with extra steps?" You need the answer ready, and §0's entity-merge finding plus §2's four broken hops are that answer.

## 4. What to steal — concretely

1. **The `provenance_edge_evidence` shape**, promoted to a first-class graph-store table. Their columns map almost exactly onto your `assertion`: `edge_id`→`proposition_id`, `pipeline_run_id`→`scope_key`+run, `source_task`→`method`, `confidence`→`confidence`, `evidence_kind`→your extension point. **Add what they lack: `polarity`, `asserted_by`, `valid_from`/`valid_to`.** Their `evidence_kind` default string `"extracted"` with a named extension point is good schema hygiene — copy the pattern of giving the discriminator a default so migrations don't need backfill.
2. **Stamp the scope-sweep watermark only on completion.** `CodeRepository.last_snapshot_id` "is stamped only after a load completes, so a crashed run can never be mistaken for an up-to-date one." Your `valid_to = run_start` sweep must be transactional with the same guarantee, or a crashed scan silently expires the world.
3. **The truth-subspace epoch guard, applied to trust.** Version your trust model; refuse a cached trust score whose `trust_model_version` ≠ current, and degrade to unranked rather than ranking on stale scores. This turns retuning the weights from a silent correctness bug into a visible degradation.
4. **Length-prefixed hash inputs.** `"enola:" + ":".join(f"{len(p)}:{p}" for p in (repo, kind, name))`. Your fingerprint concatenates subject/predicate/object/qualifiers; without length prefixes, `("ab","c")` and `("a","bc")` collide. Free correctness.
5. **The `_meta` response envelope with a state enum.** `{count, state ∈ found | indexing | build_failed | none}` on every read. An agent needs to distinguish "no facts" from "facts not indexed yet" from "the pipeline failed", and a bare empty array conflates all three. Put this on your `POST /v1/observations` 202 and on every query response.
6. **The approval-gated write flow, verbatim.** `propose → list → apply | reject`, where apply is documented as "the ONLY path that commits a write", rolls back if the affected rowcount exceeds a cap **or no longer matches the dry-run estimate**, and reject is permanent. This is the exact shape your verification agent needs before it can retire facts at scale. The re-check-against-dry-run-estimate detail is the part people forget.
7. **`identity_fields` as a declarative marker.** Their `Annotated[str, Dedup()]` / `Annotated[str, Embeddable()]` field annotations put the identity and embedding contracts at the field definition, not in a side config. Your predicate/entity-type registry should do the same — declare cardinality, identifying-vs-descriptive, and embeddability on the schema element itself.
8. **`dry_run` on every destructive operation, returning the plan.** Cognee's merge has it. Your scope sweep and any merge operation must have it, and unlike Cognee's you should **persist** the plan rather than logging it.
9. **Hook-based capture, not tool-based.** The plugin's `PreToolUse(Read)` hook injects code-graph context for the file about to be read; `PostToolUse` writes the trace. Agents forget to call tools. Hooks don't. This is the single highest-leverage idea in the repo for your risk #1.
10. **Naming.** `remember` / `recall` / `forget` is a better agent-facing verb set than anything CRUD-shaped, and `scope=[...]` on recall is a clean way to restrict a query's fact sources.

**What to explicitly not steal:** similarity-threshold entity merging in any form; destructive merges; writing a status field that no read path consults.

## 5. Build on it, or compete?

**Build on it: no, and the reason is specific.** The blocker is not missing features — it is that Cognee's **identity model is name-based and its merge policy is destructive**, and both sit below anything you could layer on. You cannot add read-time canonicalization on top of a store that deletes the duplicate. You cannot add `env` discrimination on top of `uuid5(name)`. You would be fighting the storage layer on your single most important correctness property. Add the operational cost — you must run with `ENABLE_BACKEND_ACCESS_CONTROL=false` (single-user, auth off) for any cross-dataset traversal, which contradicts your multi-writer-from-day-one requirement — and the Python/TypeScript language mismatch, and it is a bad foundation for *this* concept. It would be an excellent foundation for a different one.

**Data source: yes, and this is the genuinely useful reading.** Two concrete pipelines:

1. **Enola via Cognee as your static-analysis fact source.** `code_query` with `{"operation": "query_facts"}` or `"architecture"` returns typed, deterministic, LLM-free facts with `file_path`/`line`/`end_line` — exactly your `code_derived` method with exactly your evidence shape (repo, path, line range). You get multi-language symbol/route/storage/dependency extraction for the price of an HTTP call, and you re-key every node into your own entity-identity system on the way in, discarding theirs. The `delta` operation tells you what changed since the last index — that is your scope-sweep trigger, for free. `CodeExtractionAccount` (per-extractor coverage counters) even lets you tell a thin graph from a thin extraction, which is real input to a trust score. You could equally call `enola` directly and skip Cognee; going through Cognee buys you the repo resolution, snapshot management and delta bookkeeping.
2. **Cognee as the session-memory tier beside your graph, not beneath it.** Their plugin capture is better than yours will be for a while. Let it hold the unstructured session record; let your graph hold the typed claims. `COGX` — their portable exchange format, with importers for Mem0, Zep/Graphiti, Letta and LangMem — is a plausible ingest path if you ever want that history, and worth watching as a de-facto interchange standard.

**Bottom line for the build decision.** Cognee overlaps your *plumbing* far more than your *thesis*. They have built, independently and in production, several mechanisms you had reasoned your way to — which is validation. They have also, independently and in production, demonstrated that an open relation vocabulary makes staleness unenforceable, that name-similarity merging is where a knowledge graph goes to die, and that embedding-ranked triplet retrieval is insufficient for code (they wrote a second retriever rather than fix the first). Those three findings are your product's justification, written by someone else, in Apache-2.0 source you can cite.
