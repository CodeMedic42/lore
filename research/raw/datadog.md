# Datadog — Deep Research Dossier

**Research date:** 2026-09-24. **Primary sources:** docs.datadoghq.com (live `.md` and `llms.txt` endpoints), `DataDog/schema` GitHub repo (`service-catalog/v3`, last commit 2026-09-23), Datadog v2 OpenAPI spec (`docs.datadoghq.com/resources/json/full_spec_v2.json`), `DataDog/dd-trace-go`, `DataDog/terraform-provider-datadog`, datadoghq.com/pricing.

---

## 1. One-line

Datadog is a commercial SaaS observability platform whose Internal Developer Portal (IDP) layer — Catalog (formerly Software/Service Catalog), Scorecards, Self-Service Actions, Engineering Reports — maintains a live, telemetry-derived graph of services, infrastructure and dependencies, exposed through a JSON-Schema'd YAML entity model, a REST API, and a ~300-tool remote MCP server.

## 2. The entity model (DOCUMENTED, schema in Git)

The canonical schema lives at `github.com/DataDog/schema/tree/main/service-catalog`, with directories `v1`, `v2`, `v2.1`, `v2.2`, `v3`. It is registered with SchemaStore for IDE validation.

Four supported schema versions. The docs' own comparison table:

| Feature | v3.0 | v2.2 | v2.1 | v2.0 |
|---|---|---|---|---|
| Basic Metadata | yes | yes | yes | yes |
| Service Groupings | yes | yes | yes | |
| User Annotations | yes | yes | | |
| CI Pipeline Associations | yes | yes | | |
| Expanded Data Model | yes | | | |
| Multi-ownership | yes | | | |
| Manual Dependency Declaration | yes | | | |

**v2.2 and earlier are flat and service-only.** Required fields: `schema-version`, `dd-service`. `type` is a closed enum: `web, db, cache, function, browser, mobile, custom`. Grouping is a single scalar string field `application`.

**v3 is a graph model.** `entity.schema.json` requires `apiVersion` (enum `["v3"]`), `kind` (free string, minLength 1), `metadata`. Optional: `spec`, `integrations`, `datadog`, `extensions`.

Per-kind schema files in `v3/`: `service`, `system`, `datastore`, `queue`, `api`, `repository`, `custom`, plus `application.schema.json` explicitly marked `"[Deprecated - replaced by kind:system]"`. A commit on 2026-09-14 added an `ai_agent` entity kind schema and **reverted it the same day** — a visible signal of where they are heading.

`metadata.schema.json` (`additionalProperties: false`, requires `name`): `id` (read-only, Datadog-generated UUID; "User supplied values are ignored"), `name`, `displayName`, `description`, `tags` (array of `key:value` strings), `owner` (single string), `additionalOwners` (array of `{name, type}`), `contacts` (array of `{name, type, contact}` with a conditional `format: email` when `type == "email"`), `links` (array of `{name, type, url, provider}`, `name`/`type`/`url` required), `inheritFrom` (string `<kind>:<name>`), and `managed` — "A read-only set of Datadog managed attributes generated by Datadog."

**Relationship expression is per-kind and asymmetric in the schema:**
- `service.spec`: `lifecycle`, `tier`, `type`, `languages[]`, `dependsOn[]`, `componentOf[]`
- `system.spec`: `lifecycle`, `tier`, `type`, `components[]`, `componentOf[]`
- `datastore.spec` / `queue.spec` / `repository.spec` / `custom.spec`: `lifecycle`, `tier`, `type`, `componentOf[]`, `dependsOn[]`, `dependencyOf[]`
- `api.spec`: `interface` (`oneOf` a `fileRef` URI or an inline OpenAPI `definition`), `lifecycle`, `tier`, `type`, `implementedBy[]`, `componentOf[]`

References are strings of the form `service:myapp`, `queue:myqueue`, `datastore:mydatastore`, `library:mylibrary`, `system:my-example-system`. `lifecycle` and `tier` are **free strings with examples only** (`experimental/production/deprecated`, `"1"`/`"High"`) — not enums. This is a deliberate looseness that makes cross-org comparison unreliable.

**Extensibility is real and two-tiered.** (a) `extensions` is a free-form object, explicitly "No Datadog features are affected by this field," except two reserved keys that *are* wired to features: `datadoghq.com/dora-metrics` (git path globs for DORA attribution) and `datadoghq.com/cd-visibility`. Custom extensions are in **Limited Availability**. (b) Custom *kinds*: `custom.schema.json` constrains `kind` to `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$` (kebab-case) with the same spec fields as other kinds. Custom kinds are registered via `POST /api/v2/catalog/kind` or the UI. Critically, **a custom kind carries no custom attribute schema** — you get `lifecycle/tier/type` plus tags plus `extensions`. There is no per-kind property schema.

**Inheritance.** Explicit: `metadata.inheritFrom: <kind>:<name>`. Implicit: components of kinds `service|datastore|queue|ui` inherit *all* system metadata when exactly one system is defined in the YAML file and no `inheritFrom` is present. Multi-system membership requires repeating the component in each system's YAML.

**Integrations block** (`integrations.schema.json`): `pagerduty` (serviceURL), `opsgenie` (serviceURL + region), `jiraServiceManagementOps`, `sentry` (projectSlugs[]), `terraform` (HCP `workspaceIds[]`, pattern `^ws-[a-zA-Z0-9]+$`), `servicenow` (serviceURL with a regex requiring a 32-hex `sys_id`), `argocd` (`applications[]` as `<namespace>/<name>`). The **`datadog` block** binds the entity to telemetry: `codeLocations[{repositoryURL, paths[] globs}]`, `logs[{name, query}]`, `events[{name, query}]`, `pipelines.fingerprints[]`, and on `repository` also `performanceData.tags[]` ("APM entity tags that associates the APM Stats data with the entity").

## 3. How the graph is actually derived

This is the part that matters. Datadog's dependency graph is **overwhelmingly inferred from telemetry, not declared.**

- **APM**: distributed traces produce service-to-service edges. The Service Map doc: "Edges represent aggregate calls from one service to another."
- **Inferred services**: the Agent computes stats by span kind and aggregates **peer tags**. `DD_APM_COMPUTE_STATS_BY_SPAN_KIND` and `DD_APM_PEER_TAGS_AGGREGATION` are **default-on since Agent 7.60.0**. The documented peer-tag allowlist is explicit and long (`db.instance`, `db.name`, `db.system`, `messaging.system`, `messaging.destination.name`, `messaging.kafka.bootstrap.servers`, `aws.queue.name`, `aws.s3.bucket`, `net.peer.name`, `peer.service`, `rpc.service`, `server.address`, `topicname`, `queuename`, `tablename`, `streamname`, …). Uninstrumented dependencies are thereby materialized as `datastore`, `queue`, or third-party-API entities. Naming defaults to `net.peer.name` for external APIs and `db.instance` for databases, correctable via **renaming rules**.
- **USM**: eBPF-based, no code instrumentation, produces golden-signal metrics and dependency edges.
- **RUM**: produces `frontend app` entities.
- **Infra metrics / logs import**: an opt-in scan for `DD_SERVICE` tags, creating `kind:service` entities. The docs warn these "may expire unless you add metadata."
- **Bits AI-generated Systems**: analyzes traces + detected/declared dependencies + ownership metadata to *propose* `kind:system` entities (name, displayName, owner, description, components). Accept/edit/reject; accepted systems are tagged `created_by:ai`. "AI-generated Systems only suggest new Systems; they do not propose updates to existing ones."

**Service Map specifics:** scoped by `env` plus an optional Second Primary Tag; nodes **age out after 30 days with no traces**; the map is built from complete traces with root spans. Span summaries and service/resource statistics retained **up to 30 days**.

**Manual declaration supplements, never replaces.** The UI has an explicit **"Include Detected"** toggle: off shows only manually declared dependencies; on shows manual ones ranked above auto-detected. That toggle is the closest thing Datadog has to a provenance UI.

## 4. Infrastructure entities and cross-repo

**Resource Catalog** covers hosts, databases, storage and cloud resources, discovered via the Agent or cloud-integration crawlers (with an "extend resource collection" toggle, and an explicit warning that it can raise AWS CloudWatch costs). Each resource's side panel includes **Relationships** ("an interactive map of connections to other resources"), **Infra map** (a Cloudcraft diagram), Changes history, Security posture, Cost. Catalog itself now has an **Infrastructure** section where "Infrastructure resources link to the software entities that run on them."

**Cloudcraft in Datadog** renders live architecture diagrams for AWS, Azure, GCP, OCI and vSphere, with pluggable **overlays**: APM (draws distributed traces between cloud resources on the diagram), Cloud Cost Management (resource-level cost), Infrastructure (provider hierarchy grouping), Monitors (monitor state + launch a Bits Investigation), Observability (where the Agent is installed and which features are on), Security (exposures, misconfigurations, vulnerabilities).

**Data Streams Monitoring (DSM)** is the queue/topic topology layer and is technically the most interesting. Source (`dd-trace-go/internal/datastreams/pathway.go`): a `nodeHash` is `FNV-1 64` over `service + env + sorted allowlisted edge tags + processTags + containerTagsHash`; the allowlist is exactly `{event_type, exchange, group, kafka_cluster_id, topic, type, direction, segment_name}`. `pathwayHash = FNV-1_64(LE(nodeHash) ‖ LE(parentHash))`, so a pathway hash encodes an entire ancestry chain. A `Pathway` carries `{hash, pathwayStart, edgeStart}` and is propagated in-band with the message. `Merge` of fan-in pathways is honest about being lossy: "The current implementation samples one resulting Pathway." Latencies are aggregated client-side into **DDSketch** (`NewLogarithmicMappingWithGamma(1.015625, …)`) in **10-second buckets** for `pathwayLatency`, `edgeLatency`, `payloadSize`.

Metrics: `data_streams.latency` (tags `pathway_type` ∈ `full|edge|partial_edge|internal`, `start`, `end`, `service`, `type`, `topic`, `direction`), `data_streams.kafka.lag_seconds`, `data_streams.kafka.lag_messages`, `data_streams.sqs.dead_letter_queue.messages`, `data_streams.payload_size`. Supported: Kafka (self-hosted, MSK, Confluent Cloud), Kinesis, SNS, SQS, Azure Service Bus, Google Pub/Sub, IBM MQ, RabbitMQ, BullMQ, plus OTel; languages Java, Python, .NET, Node.js, Go, Ruby. Also **Schema Tracking** (Avro + Protobuf, per-schema first/last seen, produce/consume/error rate, schema evolution), **Kafka Console** (cluster health, message inspection), **Dead Letter Queues**. Documented limitation: "latency calculations for a pathway require single-threaded message processing"; multithreaded consumers need manual instrumentation.

**Cross-repo:** Datadog is not repo-scoped at all. Repos are just a property — `datadog.codeLocations[].repositoryURL` + glob `paths`, a `kind:repository` entity, and a GitHub integration that scans *every* readable repo for `service.datadog.yaml` / `entity.datadog.yaml` / (Backstage) `catalog-info.yaml`. Multi-repo is the default assumption, but Datadog does not index source code for the catalog — it indexes telemetry and reads declaration files.

## 5. Write capability for an external agent

**Software Catalog API (v3), all under `/api/v2/catalog/`:**
- `GET /entity` — params `page[offset]`, `page[limit]`, `filter[id]`, `filter[ref]`, `filter[name]`, `filter[kind]`, `filter[owner]`, `filter[relation][type]`, `filter[exclude_snapshot]`, `include` ∈ `{schema, raw_schema, oncall, incident, relation}`, and **`includeDiscovered`** ("includes discovered services from APM and USM that do not have entity definitions").
- `POST /entity` — upsert. Body is `oneOf` a typed v3 object **or `EntityRaw`: a raw JSON/YAML string**. Returns **202** (async ingestion), 400, 403, 429.
- `POST /entity/preview` — dry-run.
- `DELETE /entity/{entity_id}`
- `GET /relation` — `filter[type]`, `filter[from_ref]`, `filter[to_ref]`, `include` ∈ `{entity, schema}`, **`includeDiscovered`**.
- `GET|POST /kind`, `DELETE /kind/{kind_id}` — custom kind registration (`{kind, displayName, description}` or raw YAML).

**Relation type enum (10, closed):** `RelationTypeOwns`, `OwnedBy`, `DependsOn`, `DependencyOf`, `PartsOf`, `HasPart`, `OtherOwns`, `OtherOwnedBy`, `ImplementedBy`, `Implements`. This is the whole vocabulary. There is no edge-attribute mechanism — no confidence, no weight, no payload.

**Legacy Service Definition API** `/api/v2/services/definitions` (GET/POST, GET/DELETE `{service_name}`) with a `schema_version` param `v1|v2|v2.1|v2.2` — the server will project a stored definition into an older schema version on read.

**Adjacent writable surfaces:** `/api/v2/scorecard/{rules,outcomes,outcomes/batch,scorecards,campaigns,scores/{aggregation}}`; `/api/v2/dora/{deployment,deployments,failure,failures}`; `/api/v2/apicatalog/openapi` (PUT/POST/DELETE OpenAPI specs); `/api/v2/idp/entity_integrations/{integration_id}` (PUT config, e.g. `github.enabled_repos`, `jira.enabled_projects`, `pagerduty.accounts`).

**Other write paths:** Terraform `datadog_software_catalog` (v3 raw entity YAML/JSON) and `datadog_service_definition_yaml` (v2.x; needs provider ≥ 3.16.0); the GitHub integration (repo-scan, bidirectional in the sense of an "Edit in GitHub" button); the `@datadog/backstage-plugin-datadog-entity-sync-backend` npm plugin (scheduled Backstage→Datadog sync with entity filtering); ServiceNow CMDB Service Ingestion; the UI. The docs explicitly warn: "Updating the same service using both the GitHub and the API may result in unintended overwriting." There is no merge/CRDT story.

**RBAC:** `Service Catalog Read` / `Service Catalog Write` (read in Read-Only+Standard roles; write in Standard+Admin).

**MCP server — read-only for the catalog.** The remote Datadog MCP Server exposes **~304 documented tools across ~35 toolsets** (core, alerting, apm, assistant, audit-trail, cases, code-exec, cost, dashboards, data-observability, dbm, ddsql, error-tracking, experiments, feature-flags, forms, investigator, kubernetes, live-debugger, metrics-governance, networks, onboarding, product-analytics, profiling, reference-tables, remote-actions, rum, security, session-replay, sheets, software-delivery, synthetics, widgets, workflows). Selection via `?toolsets=apm,llmobs` or `toolsets=all`; exclusion via `omit_tools`. Every tool declares its required Datadog permission and the server "forwards the authenticated user's own credentials"; a read-only user calling a write tool is rejected.

**The only catalog tool is `search_datadog_entities`** (toolset `core`, permission `Service Catalog Read`): "Searches Datadog's Catalog for service identity, ownership and upstream and downstream dependencies." It supersedes the deprecated `search_datadog_services` and `search_datadog_service_dependencies`. **There is no MCP tool that creates, updates or deletes a catalog entity, relation or kind.** An agent can write monitors, notebooks, dashboards, cases, SLOs, feature flags, reference tables, spreadsheets, security rules, error-tracking triage, experiments, and can trigger workflows and Bits investigations — but to write the knowledge graph it must drop to REST/Terraform/Git.

Fair-use limits: **50 tool calls / 10 s burst, 100,000 tool calls / month.** HIPAA-eligible, not GovCloud-compatible; MCP interaction telemetry retained **120 days**.

## 6. Provenance, staleness, contradiction, temporality

**Provenance: present but thin.** The OpenAPI `EntityMeta` carries `createdAt`, `modifiedAt`, `origin`, and `ingestionSource`. `RelationMeta` carries `createdAt`, `modifiedAt`, `source`, and `definedBy`. `includeDiscovered` on both `/entity` and `/relation` separates declared from inferred. The UI exposes "Include Detected." So: **you can tell a declared edge from a derived one, and you get one string naming the source.** What you do not get is a confidence score, an evidence pointer (which trace, which span, how many observations), a competing-claim list, or a per-field provenance record. Provenance is per-object, not per-attribute.

**Staleness: implicit and aggressive, via telemetry TTL, not via a knowledge model.** Service Map nodes age out after 30 days without traces. APM span summaries and service stats retain 30 days. Telemetry-imported services "may expire unless you add metadata." Declared entities do not decay at all — a YAML-declared `dependsOn` is permanent until someone edits the file, with no mechanism to flag that it has not been corroborated by a trace in a year. The `managed` metadata block exists but is undocumented in shape.

**Contradiction: unmodeled.** When a declared dependency disagrees with the observed topology, Datadog renders both and orders manual above detected. There is no reconciliation, no flagging, no "this declaration has not been observed." Same-entity writes from GitHub and API race and overwrite; the docs' remedy is "pick one."

**Temporality: essentially absent in the Catalog, and notably present elsewhere.** Catalog entities have `createdAt`/`modifiedAt` only — no valid-time, no as-of query, no revision history in the public API. But the **Cloud SIEM entity context store** (`GET /api/v2/security_monitoring/entity_context`) is bitemporal-ish: it returns `revisions[]`, each with `attributes`, `first_seen_at`, `last_seen_at`, and supports either an interval (`from`/`to`) or a point-in-time snapshot (`as_of`), explicitly mutually exclusive. Datadog has built as-of entity querying — for security entities, not for the software graph. There is also the **Change Tracking API** (`get_change_stories`, `semantic_search_change_stories`) which gives a time-ordered stream of deployments, feature-flag and config changes for correlation, and `datadog_events`/DORA deployment events. These are event streams alongside the graph, not versions of it.

## 7. AI layer

**Bits AI** components: Bits Chat (NL exploration + action), Bits Investigation (autonomous alert RCA, steerable), Bits Code (code fixes, PRs, Slack "code channels", scheduled/signal-triggered automations), Bits Security Analyst, Bits Data Analysis, Bits Detection (autonomous monitor-coverage management), Bits Remediation. Grounding surfaces: **runbooks linked from monitor messages** (including Confluence pages, whose telemetry links Bits follows), **`bits.md`** (an org-level markdown file of tagging conventions, env/service-name normalization rules, glossary, scope rules), **Skills Library** (`SKILL.md` files, private or org-public, usable by Bits Chat, Bits Agent Builder, the Slack app, *and external agents via MCP*), and **feedback/memories**. MCP `investigator` toolset can trigger and steer investigations (`Bits Investigations Write`). Datadog is explicit that the MCP server "does not send your Datadog data to a third-party AI provider," and that a minority of tools use Datadog-hosted models for semantic search/NL-to-query.

## 8. Surrounding IDP features

Scorecards (out-of-box Production Readiness, Observability Best Practices, Ownership & Documentation; custom rules via API `pass|fail|skip` per `{rule, entity}` tuple, or via Workflow Automation with an "Update scorecard rule outcome" action, auto-tagged `source: scorecards`); **Campaigns** (time-bound initiatives grouping rules); Self-Service Actions (App Builder forms + Action Catalog + Workflow Automation, published as tiles); Software Templates; Engineering Reports (Catalog Health, DORA, Reliability Overview, Scorecards Performance, Teams Performance, Custom embedded dashboards); Endpoint Observability (HTTP endpoints auto-discovered from APM as first-class list items with ownership, monitors, synthetics, security signals); External Provider Status; a **Developer Portal dashboard data source** letting you query entity counts grouped by owner/tier/lifecycle/definition version; Homepage aggregating GitHub PRs, GitLab MRs, Jira/Linear tickets, Datadog Work Items.

## 10. Availability caveats

Schema v3.0, Self-Service Actions, Scorecards custom rules, DSM, Bits AI, Endpoint Observability and the MCP Server are all **unsupported on `app.ddog-gov.com` / `us2.ddog-gov.com`**. Custom extensions are Limited Availability. The APM MCP toolset, Investigations toolset, Metrics Governance and Live Debugger toolsets are marked Preview; Experiments and Product Analytics toolsets are off by default. v3 itself still shows an "Opt in to the Preview for the latest version of Catalog" callout on the Entity Model page.

## 11. Assessment against a living-knowledge-graph concept

Datadog's strength is that the graph is **continuously and automatically re-derived from ground truth** — you do not maintain it, and it is correct about what actually talks to what, at 30-day recency, across services, datastores, queues, endpoints, cloud resources and message pathways. Its weakness is that the *knowledge* layer on top is a thin, hand-maintained YAML annotation with a 10-verb closed relation vocabulary, free-string `tier`/`lifecycle`, no per-kind attribute schema for custom kinds, per-object rather than per-attribute provenance, no confidence, no contradiction handling, no as-of history for the software graph (despite having built exactly that for security entities), and no agent write path at all through MCP. It is an excellent *observed* topology and a weak *asserted* knowledge base.
